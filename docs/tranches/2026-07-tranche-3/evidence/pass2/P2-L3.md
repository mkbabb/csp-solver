## (a) The published-py-surface rule — whole-game vs internal-symbol

**Question.** Tranche-III prunes caller-dead PyO3 surface. But the spec treats two classes of dead
symbol unevenly with no stated rule: `futoshiki_api.rs` (a whole game's bindings) is routed to owner
ratification, while `solve_sudoku_board`, `template_count`, `PropagationStrategy`, and the
`SudokuCSP` getters are pruned unconditionally — yet all are `#[pymodule]`-registered exports of the
same published wheel (crit-spec C4). What is the **rule** that sorts a dead export into "prune freely"
vs "owner ratifies"?

**Evidence for a bright-line rule (prune internals, ratify whole surfaces).** The consumer census is
identical for both classes — zero tests-py, zero bbnf calls (compile-only gate), zero FastAPI (excised),
frontend rides wasm not the wheel (R4 §1-3, crit-spec §A). So caller-deadness alone can't discriminate;
the discriminator has to be *what the symbol means to a reader of the API*, not *who calls it*. A
whole game is a documented product capability (CLAUDE.md lists Futoshiki's surfaces as "Rust, PyO3,
wasm, API, frontend"); an internal convenience fn or a redundant getter is not. That asymmetry is a
real category line, defensible and nameable.

**Evidence against (the line is arbitrary).** `PropagationStrategy` + `propagate_with` is not a
getter — removing it strips *caller strategy selection* from Python, a capability reduction, not
hygiene (crit-P2 R2c). By meaning-to-a-reader it sits closer to "game surface" than to "dead getter."
So the bright line, drawn naively, mis-sorts at least one symbol. Any rule must handle the capability
case explicitly.

**Recommendation.** Adopt this rule, stated in the wave record:

> A caller-dead PyO3 export is pruned **unconditionally** when it is (i) a redundant accessor or alias
> of a live symbol, or (ii) an internal convenience wrapper with a live primitive underneath. It is
> **owner-ratified** when it is (iii) a whole product surface (a game's bindings) or (iv) a distinct
> user-facing capability with no live equivalent.

Under it: getters, `backtracks()` alias, the `Csp` wrapper convenience methods → prune (they wrap live
`self.inner.*`). `PropagationStrategy` → **ratify** (capability, class iv) — this corrects the spec's
unconditional prune. `futoshiki_api.rs` → ratify (class iii, → row b). `solve_sudoku_board` /
`template_count` → the rule's edge, resolved in row (c).

**Strongest counter.** The rule adds ceremony to a KISS tranche — four caller-dead symbols now need an
owner signature where "grep says zero, delete it" would ship faster. Fair. The reply: the census can't
see the crates.io downstream (the wheel *is* published to crates.io as a source crate, even if not to
PyPI), so "zero callers *here*" is not "zero callers." The rule is the cheap insurance the blind spot
demands, and it's a one-time authoring cost, not a per-symbol one.

**Ratify one of:**
1. **Adopt-as-written** — the four-class rule above; `PropagationStrategy` reclassifies to ratify.
2. **Adopt, but keep `PropagationStrategy` on the prune side** — capability-loss accepted as hygiene.
3. **Prune-all** — no rule; every caller-dead export goes, futoshiki included (collapses row b into a delete).
4. **Ratify-all** — no rule; every published-surface removal rides one 0.4.0 owner sign-off, none unconditional.

## (b) `futoshiki_api.rs` — remove vs keep-and-test

**Question.** Delete the co-equal game's 234-LOC Python surface (`FutoshikiCSP`, `FutoshikiBoard`,
`create_futoshiki_csp`, `solve_futoshiki`, `create_random_futoshiki`), or keep it and add the tests-py
coverage it currently lacks?

**Evidence for REMOVE.** Total consumer-death: zero tests-py references (`grep -rl futoshiki tests-py/`
empty), zero bbnf calls, no FastAPI, product Futoshiki solves over `wasm/src/futoshiki.rs` not the
wheel (R4 §1-2, crit-spec §A). 234 lines compiled-but-uninvoked; not in `SIBLING_DEFINITIONS`, so zero
parity coupling (R4 §4); revivable byte-for-byte from git the day a Python Futoshiki consumer appears.
Blast radius: 0 test deaths, 3 `mod.rs` edits incl. the `#[pymodule]` registration block (crit-spec B3),
bbnf green after `--update` re-vendor.

**Evidence for KEEP-and-test.** The owner's own mandate word is **"comprehensive"** (crit-P2 R1).
Sudoku and Futoshiki are co-equal shipped games; amputating one game's bindings while keeping the
other's makes the wheel *less* comprehensive and *asymmetric* — the exact opposite of the mandate,
delivered under the banner of hygiene. The compile gate is structurally *incapable of voting* on this:
it stays green whether or not Futoshiki exists, so "gate green" certifies nothing-breaks, never
should-exist. Untested-and-present is a coverage gap; the honest fix is a test, not a delete.

**Recommendation.** **Remove**, contingent on row (a) landing as rule 1 or 2. The "comprehensive"
mandate names *`sudoku_api.rs`'s* fate as the open question ("split or deprecate"); it does not
authorize keeping an unconsumed twin alive on the strength of symmetry alone. Comprehensiveness of a
*published wheel with no PyPI presence and no Python consumer* is comprehensiveness for a hypothetical.
Git makes the revival free; the tranche's whole thrust is retiring unconsumed surface.

**Strongest counter.** If the wheel ever *does* reach PyPI (row f is open, not closed), Futoshiki-in-Python
becomes a real capability the day someone `pip install`s — and having deleted it, we ship an asymmetric
API that reads as an oversight, not a decision. The keep-and-test path costs ~40 lines of test and
forecloses that embarrassment permanently. This counter has real force **iff** row (f) trends toward
PyPI; if row (f) is "never PyPI," it evaporates. **Sequence (b) after (f).**

**Ratify one of:**
1. **Remove** — delete the file + 3 mod.rs edits; revivable from git. (Recommended, if f = never-PyPI.)
2. **Keep-and-test** — retain the surface, add tests-py Futoshiki coverage (~40 LOC).
3. **Keep as-is** — retain, leave untested (status quo; declines the coverage fix).
4. **Defer to post-(f)** — decide once PyPI intent is fixed.

## (c) `solve_sudoku_board` / `template_count` under the rule

**Question.** These two live inside the *kept* `sudoku_api.rs` but are themselves caller-dead
(`sudoku_api.rs:200`, `:336`; zero tests-py — R4 §3). Prune side or ratify side of rule (a)?

**Evidence for PRUNE.** Both are convenience wrappers over live primitives — `solve_sudoku_board`
wraps the same solve path `solve_sudoku` already exposes and tests exercise; `template_count` is a
count accessor over the embedded bank. Class (ii)/(i) of the rule: internal convenience atop a live
primitive. No capability is lost — the primitive stays. This lands `sudoku_api.rs` near ~200 LOC.

**Evidence for RATIFY / keep.** `solve_sudoku_board` is a deliberately authored ergonomic entry point
(board-in, solution-out) distinct from the CSP-object path — arguably a *capability* (class iv), not a
redundant alias, since no other symbol offers the one-shot board convenience. `template_count` exposes
bank introspection nothing else surfaces. By the strict reading of rule (a), both could claim the
ratify side.

**Recommendation.** **Prune both**, as rule-class (ii). `solve_sudoku_board`'s "capability" is a thin
convenience over `solve_sudoku` + a board-marshal the tests already drive through the object path;
it's ergonomics, not a distinct capability. `template_count` is a bank accessor with no consumer and a
trivial revival. Neither clears the class-(iv) bar ("distinct capability with no live equivalent").

**Strongest counter.** If (b) removes Futoshiki *and* (c) prunes these two, the wheel narrows to a
single object-oriented Sudoku path — every ergonomic and introspection affordance gone in one wave.
A future notebook user gets a more austere API than today's. Fair, but the affordances have *zero*
current users and full git revival; austerity-with-revival beats speculative breadth under KISS.

**Ratify one of:**
1. **Prune both** — rule-class (ii); revivable from git. (Recommended.)
2. **Keep both** — treat as class-(iv) capabilities; ratify their retention.
3. **Prune `template_count`, keep `solve_sudoku_board`** — accessor goes, board-convenience stays.
4. **Keep both + add tests** — promote to load-bearing with coverage.

## (d) `propagate_stratified` — remove vs reserve vs wire-in

**Question.** `solver/monotonic.rs:58` is a complete SCC-stratified propagation routine — acyclic
constraints in one topological pass, iterative fixed-point only on cyclic SCCs — with **zero callers**
anywhere (crit-P5 C5; dispatch uses `propagate_monotonic` for `PropagationStrategy::Sweep`). The P5
demotion to `pub(crate)` trips `dead_code` under `-D warnings`, forcing a disposition. Remove it,
keep it with `#[allow(dead_code)]`, or wire it into dispatch?

**Evidence for REMOVE.** It's dead by every measure and has been since it was written; no SCC ordering
is ever computed to feed its `scc_order`/`scc_ids`/`cyclic_sccs` params. Surface honesty says delete;
git holds it for the day the SCC precompute exists. Cheapest, most honest with the tranche's thrust.

**Evidence for RESERVE (`#[allow(dead_code)]`).** It's a genuine, correct, non-trivial optimization
(the doc-comment is precise and the body is complete) — deleting it discards real work that a future
lattice-propagation pass would want. But reserving means shipping an `#[allow(dead_code)]` in a
`-D warnings` crate — an explicit smell the tranche elsewhere refuses (crit-P2 C3 flags exactly this
pattern as not-free).

**Evidence for WIRE-IN.** This is the substantive option the others dodge. The routine is *finished
code awaiting a caller* — the missing piece is the SCC decomposition that the adjacency machinery
(`solver/adjacency.rs` after the P5 relocation) already has the graph substrate to compute. Wiring it
under `PropagationStrategy::Sweep` for lattice domains is a latent perf win bbnf's six monotonic IR
passes would collect for free. It converts dead code into shipped optimization.

**Recommendation.** **Remove now, offer wire-in as a separate scoped follow-up.** Wire-in is real but
it is *not* a tranche-III encapsulation row — it needs an SCC-precompute, a correctness proof that
topological-single-pass converges for the acyclic strata, and a benchmark to show it beats the flat
sweep. That's a feature wave, not a hygiene edit. Bundling it here smuggles an optimization into a
modularization tranche. Delete the dead symbol (honest, `-D warnings`-clean), file wire-in as a
named backlog item with this memo as its spec.

**Strongest counter.** Deleting finished, correct optimization code is a real loss — the SCC substrate
is *arriving this same tranche* via the adjacency relocation, so the wire-in is closer than "someday"
suggests, and a `git revert` later re-derives it cold from a diff rather than from live code. If the
owner wants the optimization, reserve-with-`#[allow]` for one tranche is the pragmatic bridge. The
reply: `-D warnings` cleanliness is a standing invariant the tranche shouldn't puncture for a
maybe-next-wave; the diff is a perfect record.

**Ratify one of:**
1. **Remove** — delete; file wire-in as a scoped follow-up backlog item. (Recommended.)
2. **Wire-in now** — implement the SCC precompute + dispatch hook this tranche (scope expansion).
3. **Reserve** — keep with `#[allow(dead_code)]` for one tranche as a bridge.
4. **Remove, no follow-up** — delete and drop the idea entirely.

## (e) The 12+2+1 0.4.0 semver ratification

**Question.** The pub-surface sweep demotes 12 symbols to `pub(crate)`, relocates 1, and removes 2 (12+2+1, K28 — was mis-stated "13 + 2")
(`propagate_stratified` per row d; `Csp::adjacency()`, a dead accessor). Every demotion is a
breaking change to `csp-solver`'s public API. Ratify the combined W-B + W-C surface as the **0.4.0**
semver-major bump?

**Evidence for RATIFY.** Census is clean: zero external consumers of all 12+2+1 across the repo AND
bbnf's non-vendored crates, independently re-swept (crit-P5 C3) — bbnf's only optimization entry is
`solve_optimized` (`csp_strategy/mod.rs:603`), untouched. The demotions are the point of the tranche:
they tighten a leaked internal surface (`BitsetWorklist`, `SearchParams` + 5 fields, `PropResult`,
`propagate_monotonic`, `PERMANENT_DEPTH`, `ZeroCost`, `CostDomainEval`, `GAC_CORE_CALLS`, +3 forced —
`ac3_full`, `feasibility_search`, `branch_and_bound`, doubly-forced by `&Adjacency` exposure under
`private_interfaces`). SemVer says internal-tightening that removes public items is a major bump;
0.3.0 → 0.4.0 is the correct, honest signal.

**Evidence against / the caveat.** The census has **one blind spot**: the wheel and crate publish to
crates.io, and the crates.io download graph is not inspectable from here (R7a). "Zero consumers in
repo + local bbnf" is not "zero consumers on crates.io." A downstream crate pinning `csp-solver = 0.3`
and importing, say, `SearchParams` would break silently on their next `cargo update` within the 0.x
range — except 0.x semver treats *every* minor as potentially breaking, so a 0.4.0 bump is exactly the
correct signal *and* the correct protection: `^0.3` does not auto-resolve to `0.4`.

**Recommendation.** **Ratify 0.4.0.** The 0.x major-in-minor convention makes this both honest and
safe — pinned `0.3` consumers are insulated by Cargo's `^0.3` semantics; new adopters read the bump
as "surface changed." The blind spot is real but structurally handled by the version bump itself.

**Strongest counter.** If a crates.io downstream exists and tracks `csp-solver` loosely, the demotions
are a hard break they discover at compile time with no deprecation cycle. A gentler path deprecates for
one minor (0.3.x `#[deprecated]` re-exports) before removing at 0.4.0. The reply: `pub(crate)` can't be
`#[deprecated]`-shimmed cheaply (you'd keep the `pub` item aliased for a cycle, re-leaking exactly what
you're sealing), and the download census — while uninspectable — is *a priori* near-zero for a solver
crate at 0.3.0 published days ago. The bump is the deprecation signal 0.x affords.

**Ratify one of:**
1. **Ratify 0.4.0** — combined W-B+W-C surface ships as the major bump. (Recommended.)
2. **Deprecation cycle** — 0.3.x `#[deprecated]` re-exports first, remove at 0.4.0 (slower, re-leaks).
3. **Split the bump** — demotions at 0.4.0, forced-3 (`ac3_full` et al.) held to 0.5.0.
4. **Hold** — keep the 12 `pub` pending a crates.io download check before any bump.

## (f) PyPI intent — kills or keeps the abi3t row

**Question.** Will the wheel ever publish to PyPI? The artifacts table lists crates.io + npm only.
This one-liner is load-bearing twice: it settles row (b)'s "comprehensive for a hypothetical" premise,
and it decides whether the abi3t (free-threaded stable-ABI) plan row survives.

**Evidence it's PyPI-bound (keep abi3t on the roadmap).** A "comprehensive, optimal, well-structured"
PyO3 binding is a *distribution* claim, and distribution means PyPI — R1 scores the bindings SOTA on
code but docks every packaging point for the missing pyproject metadata/abi3/stubs that only matter to
a PyPI consumer (R1 §defect-1..3). If PyPI is the destination, abi3-at-py310 collapses the wheel matrix
and abi3t (PEP-803, free-threaded 3.15+) is the forward path worth planning.

**Evidence it's never PyPI (drop abi3t, keep abi3 CI-only).** Today the wheel's only two jobs are the
tests-py contract suite and bbnf's compile gate (R4 §5) — both local, neither needs PyPI. No publish
step exists in CI. abi3's matrix-collapse value is then *CI-only* (still worth it — one wheel builds
faster than four), but abi3t is planning for a free-threaded consumer that will never exist. Every
tranche instinct says don't add forward-compat surface for an absent consumer.

**Recommendation.** **Declare "no PyPI intent for this tranche; abi3 adopted CI-only; abi3t dropped."**
This is the honest read of the current tree (no publish config, no PyPI in the artifacts table) and it
cleanly resolves row (b) toward remove. If PyPI is a genuine future ambition, it's a *separate*
publish-readiness wave (stubs finalized, metadata, a release pipeline) — not a plan-row smuggled into
an encapsulation tranche.

**Strongest counter.** "No PyPI" is a self-fulfilling prophecy — declaring it forecloses the one
distribution channel that would make the Python bindings matter to anyone outside the repo, and cheaply
keeping abi3t on the roadmap costs one Cargo feature flag now versus a re-architecture later. The reply:
a feature flag with no wheel to carry it is documentation, not capability; when a real PyPI wave comes,
adding abi3t is a one-line change against a then-current PyO3 — planning it now dates immediately.

**Ratify one of:**
1. **No PyPI; abi3 CI-only; drop abi3t** — resolves (b) toward remove. (Recommended.)
2. **PyPI-bound; keep abi3 + plan abi3t** — keeps (b)'s keep-and-test counter alive.
3. **No PyPI now; keep abi3t as a documented plan row** — hedge, no wheel behind it.
4. **Defer** — decide PyPI in a later publish-readiness wave; adopt abi3 CI-only meanwhile.

## (g) Core `CspError::Timeout` — dead-vs-reserved, and its vendor blast radius

**Question.** `CspError::Timeout` has **zero constructor sites** — verified: it appears only in the
`Display` arm (`error.rs:77`), the `code()→"TIMEOUT"` arm (`error.rs:94`), the `to_pyerr` mapping
(`py/errors.rs:59`), and the enum's unit test. Nothing ever *constructs* it. Remove the dead variant
(and with it `CspTimeoutError`), or keep it as reserved taxonomy?

**Evidence for REMOVE (surface honesty).** An error variant no code path can produce is a fiction in
the public taxonomy. `code()` advertises a `"TIMEOUT"` a caller will never receive from this engine;
`CspTimeoutError` is an exported exception class that can't be raised from Rust. Deleting it makes the
taxonomy *true*.

**Evidence for RESERVE.** The `"TIMEOUT"` code is *live at other surfaces* — the wasm wire and the
(now-excised) FastAPI envelope both carry a TIMEOUT code independent of the py exception
(`synthesis-pass2.md:82`; the frontend's `TEACHER_RED_CODES` holds it). A wall-clock deadline *is* a
real solver outcome the config models (`cancel` + `node_budget`); the variant is arguably reserved
taxonomy awaiting the driver that constructs it, not dead weight. Keeping it aligns the Rust taxonomy
with the codes the other surfaces already speak.

**The blast radius (why this is not a free delete).** Removal is not one-line. `py/errors.rs:53-61`
is an **exhaustive** match — dropping the arm alone is `E0004` (proven, crit-spec B2). So removal
forces: the variant def (`error.rs:63`), the `Display` arm (`:77`), the `code()` arm (`:94`), the enum
unit test, the `to_pyerr` arm (`py/errors.rs:59`), the `CspTimeoutError` `create_exception!` +
its `mod.rs` dict registration — **and**, because bbnf vendors `csp-solver/src` byte-identically, all
of it must mirror into `/Users/mkbabb/Programming/bbnf-lang/crates/csp-solver/src/{error.rs, py/errors.rs}`
via `--update`, then survive `--verify` under both cfg branches. A five-file core edit with a vendor
re-sync tail.

**Recommendation.** **Reserve** — keep the variant, keep `CspTimeoutError` exported. The `"TIMEOUT"`
code is genuinely live across wasm/frontend/(former)API; the Rust variant is the taxonomy's honest
placeholder for an outcome the config already models and a future cancel-driver will construct. The
removal's blast radius (five core files + a vendor mirror re-sync + both-cfg `--verify`) is
disproportionate to the honesty gain, and it desynchronizes the Rust taxonomy from the codes every
other surface speaks. Confirm no doc contract *names* `CspTimeoutError` as constructable (it doesn't —
docs list it as taxonomy, not a raised exception) and leave it reserved.

**Strongest counter.** "Reserved for a future driver" is exactly the speculative-surface argument the
tranche rejects everywhere else (futoshiki, `propagate_stratified`) — consistency says an unconstructable
variant is dead and should go like the rest. The reply: unlike those, this variant's `code()` string is
*already consumed live at three other surfaces*, so it isn't speculative — it's the Rust half of a
taxonomy contract the rest of the stack already honors. Deleting it would make Rust the *only* surface
that can't speak TIMEOUT.

**Ratify one of:**
1. **Reserve** — keep variant + `CspTimeoutError`; it mirrors live wasm/FE TIMEOUT codes. (Recommended.)
2. **Remove** — delete variant + class + arm; mirror the 5-file edit into the bbnf vendor via `--update`.
3. **Reserve + document** — keep, add a `// reserved: no constructor until cancel-driver` note at the def.
4. **Defer to W-C** — decide inside the core-encapsulation wave with the vendor gate run live (R11).

## (h) The `mod.rs`-rename mechanical follow-up

**Question.** The SOTA-idiom Rust module form is the self-named file (`foo.rs` beside `foo/`) over
`foo/mod.rs` — enforceable via `clippy.self_named_module_files` (R8 G1/A1). The crate has 11 `mod.rs`
files. The spec **rejected** this as a tranche-III wave row (pure rename churn, git-history noise,
zero encapsulation gain during an active campaign). Does the owner want it as a **separate one-commit
mechanical follow-up** with the lint enabled — or dropped entirely?

**Evidence for the follow-up.** It's a real, tool-endorsed idiom (Rust Reference frames `mod.rs` as
legacy; the Book presents the self-named form). It makes each module an atomic unit for
move/rename/review and ends the "eleven files named `mod.rs` open in one editor" confusion. As a
single isolated commit with the lint as the guard, it's mechanically safe and self-documenting.

**Evidence against (why it was rejected as a wave row).** Zero encapsulation gain — it's pure
house-style. It rewrites 11 files' paths, scattering `git blame` noise across the whole crate mid-tranche,
and it collides with the *other* renames this tranche lands (`sudoku_api.rs → sudoku.rs`,
`adjacency.rs → solver/adjacency.rs`), compounding history churn. The KISS bar rejected it correctly
as a wave row.

**Recommendation.** **Offer it as a post-tranche one-commit follow-up, owner-gated, not a tranche-III
deliverable.** Land it *after* the tranche's own renames settle (so the two churn events don't
interleave), as a single commit that flips all 11 files and enables `self_named_module_files = "warn"`
in one shot. The lint then prevents backslide for free. It's a legitimate cleanup that simply doesn't
belong *inside* an encapsulation tranche.

**Strongest counter.** Deferring a pure-mechanical, lint-guarded cleanup to "later" is how it never
happens — bundling it into this tranche's already-live rename set (which touches the module tree
anyway) would fold the churn into one campaign instead of spawning a second. The reply: this tranche's
renames are *encapsulation-motivated* (removing suffixes, relocating for visibility); a blanket
`mod.rs` flip is *style-motivated* and 11× wider — merging them muddies the tranche's record of *why*
each file moved. Keep the motivations separate.

**Ratify one of:**
1. **Post-tranche follow-up** — one commit, all 11 files, lint enabled; lands after tranche renames. (Recommended.)
2. **Fold into this tranche** — do the flip inside W-C/W-D alongside the other renames.
3. **Drop** — no rename, no lint; `mod.rs` form stays.
4. **Lint-only** — enable `self_named_module_files = "warn"` now as a ratchet, convert files opportunistically.
