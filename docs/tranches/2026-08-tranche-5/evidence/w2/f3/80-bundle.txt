## THE ONE ROW THAT MISSED, STATED PLAINLY

'main chunk not larger' is MISSED BY 0.37 kB (+0.17%; +0.16 kB gzipped). It is not a
measurement artefact and it is not rounded away:

  Before, the main chunk carried SUDOKU'S OWN client (the eager row is a static import, so
  useSudoku -> useSolver rode the main chunk); the other four each carried a private copy
  inside their own lazy spec chunk. After, the main chunk carries THE client — the one that
  serves all five — and the four lazy chunks carry none. The one client is a little larger
  than sudoku's solo client was, because it is parameterized over five families instead of
  hard-coded to one. That difference, 0.37 kB, is the whole overage.

  It buys: -71.01 kB of duplicated worker code, -6.73 kB across the four lazy chunks, and
  -76.35 kB of dist JS overall. It also buys the thing bytes do not show — four cold wasm
  instantiations that no longer happen, because a lazy game's first deal now lands on the
  worker the eager game already warmed.

  The lead's call, not the lane's: accept the 0.37 kB against the -76.35 kB, or restamp the
  row. This lane did NOT tune the number to fit — the only way to hold 'not larger' would
  have been to keep the eager game off the shared client, which is the collapse itself.
