§1 — THE API SURFACE, MEASURED
------------------------------------------------------------------------------------------
The row asks for a webkit arm "where the PW device API allows". Allowance was measured, not
assumed: a standalone probe drove `webkit.launch()` and `chromium.launch()` against the live
app under `devices["iPhone 13"]` and under an explicit `{viewport 390×844, hasTouch, isMobile}`
context, then exercised every API the two mobile specs reach.

WHAT PLAYWRIGHT'S WEBKIT ALLOWS (all measured true under mobile emulation):

  isMobile + hasTouch accepted        newContext() does not throw; no "not supported" path
  descriptor viewport honoured        innerWidth 390 / innerHeight 664 (iPhone 13), 390×844
                                      (explicit) — the meta-viewport IS taken into account
  deviceScaleFactor honoured          devicePixelRatio 3 under the iPhone 13 descriptor
  (pointer: coarse)                   true          ← the media the whole coarse branch keys on
  (hover: none)                       true
  (any-pointer: coarse)               true
  ontouchstart in window              true
  locator.tap()                       OK
  page.addInitScript()                OK            ← keyboard-avoid's fake visualViewport
  window.visualViewport redefinable   OK            ← the 296px keypad-band probe's mechanism

  ⇒ Both `mobile-*.spec.ts` files are FULLY runnable in PW-WebKit. Nothing they do is gated.

WHAT IT REFUSES — the API cites, verbatim:

  1. page.mouse.wheel(…)
       Error: "mouse.wheel: Mouse wheel is not supported in mobile WebKit"
       Source: playwright-core 1.61.1 — the WebKit raw-mouse impl throws whenever
       `browserContext._options.isMobile` is set, before `Page.updateScrollingState`.
       (`node_modules/playwright-core/lib/coreBundle.js`, the WebKit RawMouse `wheel` method.)
       Chromium under the same descriptor: OK.
       REACHED BY THESE SPECS? No. `grep -n "mouse.wheel" e2e/mobile-*.spec.ts` → nothing.
       The specs scroll by assigning `doc.scrollTop` in-page (mobile-platform, `seat()`),
       which is engine-neutral and measured working in both.

  2. browserContext.grantPermissions(['clipboard-read','clipboard-write'])
       Error: "browserContext.grantPermissions: Unknown permission: clipboard-write"
       Chromium under the same descriptor: OK.
       REACHED BY? `share-truth.spec.ts:65`. This is the one exclusion that stays — §6.

  3. navigator.maxTouchPoints
       WebKit reports 0 under emulation; Chromium reports 1. Not an error, a difference —
       recorded because it is the shape of a future false-green.
       REACHED BY? No spec reads it (`grep -rn maxTouchPoints e2e/` → nothing).

ENGINE PRECEDENCE — the question the un-pinning turns on. `devices["iPhone 13"]` carries
`defaultBrowserType: "webkit"`. Removing a file's explicit `browserName` therefore risks the
chromium project silently running webkit. Measured with a throwaway config declaring both
projects and a spec doing `test.use({...devices["iPhone 13"]})`:

       RESOLVED browserName=chromium isMobile=true hasTouch=true
       RESOLVED browserName=webkit   isMobile=true hasTouch=true

  ⇒ An explicit project-level `browserName` outranks a file-level `defaultBrowserType`.
    (`browserName`'s fixture default IS `defaultBrowserType`; a project that overrides
    `browserName` outright replaces the fixture, so the file's change to `defaultBrowserType`
    no longer reaches it.) The descriptor's default is inert under both projects. This is
    what makes `test.use(devices["iPhone 13"])` — with no engine key at all — correct.


§2 — THE TWO COMPUTED-STYLE DIVERGENCES, AND THE ABLATION THAT KEEPS THEM HONEST
------------------------------------------------------------------------------------------
Widening surfaced exactly two places where the engines PUBLISH differently. Neither is a
product difference; both were measured, and both assertion sites now read what is actually
there rather than what Chromium happens to expose.

  A. user-select on `.board-cells`
       chromium: getPropertyValue("user-select") = "none"  · "-webkit-user-select" = "none"
                 CSS.supports("user-select","none") = true
       webkit:   getPropertyValue("user-select") = ""      · "-webkit-user-select" = "none"
                 CSS.supports("user-select","none") = FALSE — the unprefixed property does
                 not exist there, and `getComputedStyle(el).userSelect` is `undefined`
                 (which is the literal RED: "Expected: none / Received: undefined").
       ABLATION (a fresh <div> outside `.board-cells`, i.e. the rule deleted):
                 chromium "auto"/"auto"  ·  webkit ""/"text"
       ⇒ Reading `user-select || -webkit-user-select` still fails when the rule dies, in both
         engines. The assertion got engine-honest, not weaker.

  B. -webkit-text-size-adjust on <html>
       chromium: computed "100%"  ·  CSS.supports(…,"100%") = true
       webkit:   computed ""      ·  CSS.supports(…,"100%") = FALSE
       It is an iOS-WebKit property. Playwright's WebKit is desktop Safari plus mobile
       EMULATION, not iOS, so the property is not implemented and publishes nothing.
       The preflight DOES author it — found in the loaded CSS in both engines:
           "html, :host { line-height: 1.5; -webkit-text-size-adjust: 100% …"
       ⇒ The row now asserts the AUTHORED declaration (bites in both engines) and pins the
         computed read to the engine's own `CSS.supports` answer. No skip, no fallback: both
         arms red if either engine changes what it publishes.

  C. -webkit-touch-callout — worth recording because the existing comment was half right.
       CSS.supports("-webkit-touch-callout","none") is FALSE in Chromium AND in PW-WebKit.
       The raw-CSS grep was never a chromium workaround; it is the only instrument either
       engine leaves. Comment corrected in place; the assertion is unchanged.

  Unchanged and green in both engines: overscroll-behavior-y "contain", touch-action
  "manipulation", -webkit-tap-highlight-color "rgba(0, 0, 0, 0)", viewport-fit=cover,
  the `.corner-right` safe-area authorship walk.

§5 — THE CONFIG-LINT AND ITS CANARY
------------------------------------------------------------------------------------------
web/frontend/scripts/check-pw-projects.mjs · `npm run test:e2e:projects` (carries --self-test)
CI step: fragments/config-lint.yml (integrator lane merges it into the `e2e:` job).

Why a lint at all: a narrowing is invisible by construction — the suite passes FASTER and
greener when it covers less. Nothing in T4 watched the matrix, which is how 19 tests ran in
one engine for a campaign while every count read green.

It does not parse the config's prose. It asks Playwright for the resolved matrix
(`--list --reporter=json`) and imports the config objects for each project's declared engine
(Node 26 runs the .ts configs directly), then holds both against a manifest that must be
edited on purpose. Five checks, all evaluated before the verdict:

  1 DECLARED MATRIX   the 9 (project, engine) pairs across 3 configs, exactly
  2 SPEC OWNERSHIP    all 20 specs claimed by exactly one config; no orphans, no double-claims
  3 ENGINE COVERAGE   every spec in BOTH engines unless HOLDOUTS says why
  4 HOLDOUTS CLOSED   a stale holdout (spec now runs wider) reds — the record follows the code
  5 COUNT FLOORS      per-project counts never fall below the recorded floor
