## Row 1.5 — cargo-audit gains a schedule

**Landed**: `.github/workflows/security-audit.yml` (new, 93 lines, 64 of them a posture comment).
`schedule: cron '17 13 * * *'` + `workflow_dispatch:` + `permissions: contents: read` +
one job, `cargo-audit`, mirroring `ci.yml:769-785` command-for-command.

**Cron choice.** 13:17 UTC = 09:17 US/Eastern (08:17 EST) — the owner's morning year-round,
off-hour and off-minute, away from the top-of-hour queue surge where GitHub's scheduler
delays and drops are likeliest.

**Posture, documented in the workflow's own comments.**

| claim | disposition |
|---|---|
| what fails | a VULNERABILITY against any crate in `Cargo.lock`. Unconditional — no allowlist, no `--ignore`, no `continue-on-error` |
| what does not | informational `unmaintained`/`unsound`/`notice`, per `cargo audit`'s default. Kept at default deliberately: `--deny warnings` would red daily on two conditions nobody can fix, and an always-red gate is an unread gate |
| the standing census | 0 vulnerabilities · 2 allowed warnings — RUSTSEC-2025-0141 (bincode 1.3.3), RUSTSEC-2026-0173 (proc-macro-error2 2.0.1), both transitive. 1,178 advisories loaded, 122 crate dependencies scanned |
| what it cannot see | `Cargo.lock` only. The npm surface — where both live Dependabot alerts sit, r3's supply-chain asymmetry — is row 1.15's, and the workflow says so rather than implying coverage |
| why `ci.yml`'s lane stays | it is the PRE-MERGE gate; a PR adding a vulnerable dep must red before it lands, not up to 24 h later. Same command, same rule, different trigger — noted in both files so the two oracles cannot silently diverge |

**The fine print, recorded not hidden.** GitHub disables scheduled workflows after 60 days of
repository inactivity, and re-enabling is manual — so the repo quiet enough to need this check
is exactly the repo that loses it. That is V5's blindness reappearing one level up. Mitigations
named in the file: `workflow_dispatch` (a human can always fire it) and `ci.yml`'s push lane.
Second: `schedule:` fires on the DEFAULT BRANCH only, and cron on shared runners is best-effort
— "roughly daily", never real-time.

**Born-RED**, two arms, both banked before the file existed:

- ARM 1, the config probe — `r1.5-schedule-RED-at-HEAD.txt`. `grep -rnE '^\s*(schedule|workflow_dispatch|repository_dispatch):' .github/workflows/` → **exit 1, no match**; `cron:` → no match; the tree's only trigger block is `ci.yml:71-75` (`pull_request` + `push`). Corroborates r2 §4 exactly.

Vulnerability reds, informational does not — the documented asymmetry observed on both arms rather than asserted. Repo `Cargo.lock` md5 `b97f9561b5eb4b21707ceeebc14c52fb`, `git status` clean after.

**GREEN after**: `r1.5-schedule-GREEN-after-cure.txt` — the same probe now hits, the YAML parses

## Row 1.12 — the wasm pkg's resolution contract (I3 NARROWED / N2)

**The cure is in the generator, not the artifact.** `pkg/package.json` is gitignored and minted
wholesale by wasm-pack, so patching the file is patching a build output. Landed instead:

- `csp-solver/wasm/scripts/pkg-exports.mjs` — one constant, read forwards and backwards.
  `--write` stamps the map onto the artifact; `--check` asserts the manifest carries EXACTLY
  that map (missing rows AND undeclared extra rows both red), every target exists, and every
  non-`.` subpath resolves for a real consumer. Gate and postprocess share the constant, so
  they cannot drift. The resolution probe links the pkg into a throwaway `node_modules` and
  asks Node — it tests the shipped artifact, not this repo's frontend install state.
- `csp-solver/wasm/Makefile` — `wasm:` gains `node scripts/pkg-exports.mjs --write` after the
  build; new `exports-check:` target runs `--check`. `web/frontend`'s `prebuild` already routes
  through `make -C ../../csp-solver/wasm wasm`, so the postprocess is on the local ship path
  from this commit forward.

**The map**, three rows, deliberately closed:

```json
"exports": {
  ".": { "types": "./csp_solver_wasm.d.ts", "default": "./csp_solver_wasm.js" },
  "./csp_solver_wasm_bg.wasm": "./csp_solver_wasm_bg.wasm",
  "./package.json": "./package.json"
}
```

Vite strips `?url` before resolution, so the workers' `…_bg.wasm?url` needs the bare subpath row.
`types` precedes `default` — condition order is resolution order, and `web/frontend` runs
`moduleResolution: "bundler"`, which honours the map.

**A deliberate narrowing, flagged.** `./csp_solver_wasm.js` is now UNEXPORTED
(`ERR_PACKAGE_PATH_NOT_EXPORTED`). Today's legacy fallback resolves it; the map does not. Nothing
in this repo deep-imports it — the bare `.` specifier is the canonical entry, and a closed surface
is the whole value of an exports map. A registry consumer outside this tree who deep-imports the
JS entry would break. Reversible in one line if the team lead wants the row; recorded here rather
than decided silently.

**Born-RED, then the canary, then green** — in that order:

| bank | result |
|---|---|
| `r1.12-exports-RED-at-HEAD.txt` | `--check` on the untouched HEAD artifact → **RED, exit 1**, `exports (absent)`. Manifest md5 `253050d6e0d52b89cbabf75e1d5b20b0` — byte-identical to the one r2 probed |
| `r1.12-exports-CANARY-stateB.txt` | the N2 drift scenario on a COPY (map present, no `.wasm` row) → **`ERR_PACKAGE_PATH_NOT_EXPORTED`**, exit 1. Reproduces r2's state B verbatim. Real pkg md5 unchanged after |
| `r1.12-exports-GREEN-after-cure.txt` | after `make wasm` → **GREEN, exit 0**, 3 rows, both subpaths resolve. Manifest md5 `1eb6e14c7765f5345bd03df1f4e83290` |
| `r1.12-consumer-build-GREEN.txt` | `vue-tsc --noEmit` exit 0 · `vite build` exit 0 · 5 worker chunks emitted · 1 wasm asset at 122,385 B |
| `publish-dryrun.txt` | the dry run + tarball-realized resolution + the no-token proof |

**Byte band.** `csp_solver_wasm_bg.wasm` = **122,385 B** after regen, delta **0 B** against the
pre-cure measurement of the same file, **5,115 B** under the 127,500 B fail band (95.98% of
budget). The map is a `package.json` edit and cannot move the binary — re-measured anyway, and
re-measured a third time inside the tarball.

**`npm publish --dry-run`** (`publish-dryrun.txt`, NO real publish): `@mkbabb/csp-solver-wasm@0.6.0`,
6 files, 66.5 kB packed / 214.6 kB unpacked, shasum `4b8772c63b44386dd41fa9f761a24d541746f30f`,
exit 0. Then the part that actually matters — the tarball is unpacked into a throwaway
`node_modules`, exactly what a registry consumer receives, and Node resolves from THERE: bare
entry OK, `…_bg.wasm` OK, `package.json` OK, undeclared `.js` → `ERR_PACKAGE_PATH_NOT_EXPORTED`.
Packing has its own surface (`files`), so only the tarball proves what a consumer gets. §6 proves
the check needs **no NPM token**: with empty user+global npmrc it warns and exits 0, so the CI
lane runs on a bare runner with no publish capability.

**Fragment**: `fragments/publish-dryrun.yml` — valid 2-document YAML, both documents parse.

- **PART A** is a REQUIRED 2-step insert into the EXISTING `build-lean-wasm` job (`ci.yml` ~:361,
  between the build and the upload). CI calls `wasm-pack build` directly and uploads `pkg/` as
  `lean-wasm-pkg`, which `frontend`, `e2e` and `twiggy` all download — the Makefile is **not** on
  that path. Without Part A, CI's artifact carries a different resolution contract than the local
  ship recipe produces and every downstream lane tests the wrong package. Proxy ≠ surface.
- **PART B** is the new `wasm-publish-dryrun` job: `needs: build-lean-wasm`, downloads the very
  artifact the other lanes consume, then `--check` → `npm publish --dry-run` → tarball resolution
  → an independent re-derivation of the 127,500 B band. Its shell steps were executed verbatim
  locally (the tarball-resolution block exits 0).
- Explicitly NO `NODE_AUTH_TOKEN`. The job must not be able to publish.
