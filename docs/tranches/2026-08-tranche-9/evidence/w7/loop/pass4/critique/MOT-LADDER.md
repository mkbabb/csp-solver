### 2.1 THE RATCHET STILL LIES, AT A NEW DOOR — third occurrence of the class

On a scratch copy of this tree I shortened a shipped character by half and walked it past the
whole gate in four edits, each of which is the shape a retuner's commit takes:

  ✓ B1 NAMED   ✓ B6 RATCHET   ✓ G-DOCK-BAND   ✓ G-GUARD   ✓ G-REFUSE-ONE-HOME

(`logs/attack-3-moved-row-GREEN-exit0.log`; the two controls that RED are banked beside it.)

The mechanism is that **both of B6's escape classes are unvalued**. `movedKeys` silences the
orphan clause for a key with no requirement that a new key exist or that its value be ≥ the banked
one (`b6NoShorten` step 3: `if (live.has(key) || movedKeys.has(key)) continue`). And the RETUNE
class is worse: I set `rise: 520 → 100` on this tree and **B6 stayed green**, because the `rise`
RETUNE row names a cite and no target value — one owner-cited shortening permanently disarms the
ratchet for that rung. Only G-DOCK-BAND caught it, and only because `rise` happens to be the one
rung a second gate watches.

This is the campaign's second-occurrence rule reaching its third bite: pass 2, a site-keyed bank
could not see a rung sabotage; pass 3, a rung-keyed bank could not see a site sabotage behind a
prose edit; pass 4, a masked-and-orphan-clamped bank cannot see a site sabotage behind a ledger
row. **The invariant to state is that an escape row must carry its value.** The cure is two
sentences of code: a `RETUNE` row carries `to: <ms>` and B6 REDs unless the new value equals it; a
`MOVED` row carries `newKey` and B6 REDs unless that key exists at ≥ the banked value. Both belong
in the self-test as controls, in the same form as the two-step attack.

A latent third door, unexploited today but one row away: `b6NoShorten`'s site loop keys the RETUNE
exemption on the **file** (`retuned.has(r.key.split(" :: ")[0])`) while the bank is keyed on the
full site. The single RETUNE row names `MOTION.rungs`, so nothing is exempt now; the first RETUNE
row that names a real file exempts every length in it.

### 2.2 THE BALLOT'S HEADLINE NUMBER NAMES THE WRONG ENGINE, IN THE ONE UNMATCHED CELL

The README's ballot sentence reads: *"Choosing 520 over 600 is choosing 5411 px/s over 4739 px/s
at the worst pose (768×1024, **webkit**)."* From the lane's own `motion-dock-series.json`:

| pose · engine | 440 | 480 | **520** | 560 | **600** | 700 |
| --- | --- | --- | --- | --- | --- | --- |

| 768×1024 **webkit** | 6203 | 5725 | **5314** | 4994 | **4607** | 4011 |

every clock is chromium 768×1024, so the table is right about the *value* and wrong about the
*engine* in the one row the owner reads — and the two banked frames are webkit, so the ballot's

Worse, that cell is the only one whose excursion is not matched:

| pose · engine | travel at 440 / 480 / 520 / 560 / 600 / 700 | spread |
