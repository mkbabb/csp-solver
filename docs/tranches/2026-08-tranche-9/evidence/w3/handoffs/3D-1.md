## The defect, measured

`evidence/w3/phone-head-order-HEAD.txt`, both engines, at HEAD:

```
390×844   badge .mobile-attribution (inside main > .board-group)
          badge x=0    toggle x=336    badgeFirstInPaint=true  badgeFirstInDom=false  agree=FALSE
1280×800  badge .corner-left (page root)
          badge x=0    toggle x=1124   badgeFirstInPaint=true  badgeFirstInDom=true   agree=true
```

The head carries two marks: the `@mbabb` badge on the left and the celestial toggle on the right.
On a desktop the badge is `.corner-left`, declared in the page root before `.corner-right`, so DOM
order and paint order agree. On a phone the desktop badge is `display: none` and the badge that
paints is the `mobile` one — which is mounted a whole subtree away, inside
`<main> > .board-group`, AFTER `.corner-right`. So the phone visits the RIGHT-hand mark first and
the LEFT-hand mark second, and the desktop visits them the other way round.

`positiveTabindex: 0` on the page, so DOM order **is** tab order here — there is no tabindex to
blame and no tabindex cure. Confirmed by a live Tab walk in chromium at 390×844:
`sun-moon-toggle @ x=336` then `attribution-trigger @ x=0` (`evidence/w3/gallery-geom-HEAD.txt`).

## Why it costs zero pixels, proven rather than asserted

`.mobile-attribution` is `position: fixed; top: var(--head-rule, 0.75rem); left: 0` — out of flow
already, and its own CSS says so ("The mobile pose LEAVES THE FLOW to get here",
`AttributionCard.vue:126-128`). A fixed box is laid out against the viewport UNLESS an ancestor
establishes a containing block, so the question was measured rather than assumed
(`scratchpad probe, 390×844`): walking every ancestor of `.mobile-attribution` —
`.board-group`, `main.main-content`, `.page-root`, the mount div, `body`, `html` — none carries a
`transform`, `filter`, `perspective`, `backdrop-filter`, `contain: paint/layout`, or a
`will-change` naming any of them. `ancestorsMakingContainingBlock: []`. The badge's rect is
`[0, 0, 75.5, 39.8]` and stays there wherever in the page it is declared.

The `@media print` rule at `src/assets/index.css:897` names `.mobile-attribution` flat, with no
`.board-group` ancestor in the selector, and no other rule in the estate mentions the class. The
comment at `App.vue:812-814` ("it stays mounted HERE so the gallery's v-show and `closeAll` keep
their one owner") is honoured by the move: both the `v-show` and the `ref` come along.

## If you want it gated

The portable assertion is DOM order, not a Tab walk, and the reason is measured: Playwright's
WebKit honours macOS's default keyboard access, so Tab visits form inputs only and never lands on
a `<button>` at all — a Tab-walk row would silently assert nothing in one of the two engines
(`evidence/w3/gallery-geom-HEAD.txt`, the webkit walk reads
`["input.cell-native-input", "BODY", "input.cell-native-input", …]`). The claim that survives both
engines is the one already measured above:

```ts
// the head's two marks are visited in the order they are painted, at every width
const agree = await page.evaluate(() => {
  const painted = (el: Element | null) => !!el && el.getBoundingClientRect().width > 0;
  const m = document.querySelector('.mobile-attribution .attribution-trigger');
  const d = document.querySelector('.corner-left .attribution-trigger');
  const badge = painted(m) ? m! : d!;
  const toggle = document.querySelector('.corner-right button.sun-moon-toggle')!;
  const domFirst = (badge.compareDocumentPosition(toggle) & Node.DOCUMENT_POSITION_FOLLOWING) !== 0;
  const paintFirst =
    badge.getBoundingClientRect().left < toggle.getBoundingClientRect().left;
  return domFirst === paintFirst;
});
expect(agree, 'the head is read in the order it is painted').toBe(true);
```
