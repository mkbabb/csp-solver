# T9-W6 lane 6D-R15 — THE ARMED GUARD RE-ANCHORS

Spec: `waves/T9-W6-substrate.md` §6.4, second bullet. `--guard-x` was measured once at arm and
never invalidated; a resize or rotation while armed re-creates the geometry T8-R15 closed. The
wave's ruling: the armed guard re-anchors or dismisses, either is lawful, silence is not.

## THE CHOICE: IT RE-ANCHORS

Named from the tree, not from taste.

1. The deck's own answer to a resize is `useCarouselGlide`'s instant re-pin
   (`useCarouselGlide.ts:534`, `jumpTo(currentIndex)`) — never a teardown. The ribbon rides that
   same geometry, so the ribbon's answer is the same shape.
2. `syncFromScroll` (`GameGallery.vue:469-477`) retires the ribbon only when the index CHANGES.
   A re-pin keeps the index, so the tree already rules that a resize is the same card in a new
   place. A dismiss-on-resize would contradict a rule already written down.
3. The note is an `aria-modal` `alertdialog` holding focus and an unanswered consent question. A
   window that changed size is not an answer to it.

## WHAT IT ACTUALLY COSTS AT HEAD — worse than a miss

The live frames say it plainly. `r15-frames/BEFORE-390-stale-anchor-chromium.png`: after a
1440×900 → 390×844 rotation the note keeps `--guard-x: 352px` on a 390px frame, so the ribbon
hangs off the right edge with its title truncated mid-word and the **destructive verb entirely
off screen**. The prompt cannot be answered, only escaped. `AFTER-390-reanchored-chromium.png` is
the same pose cured: whole note, both verbs reachable, centred on the card it names.

The edge clamp (`GUARD_EDGE_PX`, the thing that keeps the note WHOLE) never re-ran either — it is
inside `anchorGuard`, and `anchorGuard` was the thing that never ran again.

## THE CURE (`GameGallery.vue`, the `guardX` seam only)

Two arms, both re-running the existing `anchorGuard`. Nothing else moved; no new state, no new
string, no new prop.

- A `ResizeObserver` on the viewport, **constructed after the glide's** (the composable registers
  its `onMounted` at the `useCarouselGlide` call, this one below it, and Vue runs them in
  registration order), so it is broadcast after `jumpTo` has written the new `scrollLeft`. A
  `window.resize` listener would fire BEFORE the broadcast and re-measure a track about to move.
- A `passive` `scroll` listener on the viewport, because that ordering is a courtesy and not a
  guarantee: WebKit re-snaps on its own after a resize. Under an armed ribbon the deck cannot
  travel for any other reason (every verb that moves it dismisses first), so a scroll here means
  exactly "the track moved beneath the note".

### The one suspicion, killed with the negative control

WebKit sometimes retires the ribbon during the rotation instead of moving it — the deck's native
snap lands on card 1, `reportSnap` → `syncFromScroll(1)` → the EXISTING `dismissGuard`. That is a
HEAD behaviour, not the cure's: fully ablated, `head-390-wk` measured **0 of 4** WebKit arms
surviving, the worst rate recorded in any condition. Chromium is the clean discriminator and it
is flat: **6/6 survive ablated** (at 161px) and **6/6 survive cured** (at 0.00px). `anchorGuard`
has no path to `activeIndex` or `dismissGuard`; it cannot dismiss anything.
