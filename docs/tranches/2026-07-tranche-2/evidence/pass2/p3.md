## The question

Does extending the W8 grain-hoist to the board-size-transition layer (L28 F1 proposal) cut the size-switch raster (842 ms/s desktop / 133 ms frame @4× claimed) without visual regression?

## The build

Two edits, both in the F1 "no grain-static while geometry animates" discipline:

1. **`HandDrawnGrid.vue`** — the transition `<g>` (mounted only while `animState !== 'drawn'`) drops its `:filter="pathsVisible ? 'url(#grain-static)' : undefined"` binding outright. The settled look is owned entirely by the pre-baked, opacity-toggled steady siblings (untouched).
2. **`HandwrittenGlyph.vue`** — per-glyph `grain-static` is suppressed while the reveal draw-in tweens dashoffset (a reactive `grainOn` ref, set false at arm, restored in the tween's `onComplete`; also restored on `cleanupAnimations()` so a stopped draw-in never strands the tooth off). One filtered raster per glyph total instead of one per frame per glyph.

Built in `wt-p3` on wt-head's node_modules; BEFORE build reproduces verify-28's HEAD bundle byte-exact (`index-CZHZBZxm.js`); AFTER (`index-fCKonWHt.js`, +30 B) is clean under `vue-tsc -b`.

**Source-forensics correction to L28 F1's root-cause narrative** (measurement unaffected): at HEAD the transition `<g>` was NEVER filtered during the ~800 ms draw-in — `pathsVisible` is false until `animateDrawIn` completes (`usePathAnimation.ts:116`), so `:filter` resolved `undefined` the whole tween. The filtered animators in the switch window were (a) the **erase phase** (`pathsVisible` still true from the prior steady state, boil ticking `d` + dashoffsets tweening under the full-board filter) and (b) the **per-glyph reveal draw-ins** (~150–160 givens on a 16×16, each a filtered path re-rastering per frame for its 350 ms tween), plus a 1–2-frame filtered flash at draw-complete. F1's "re-rasterizes the entire 16×16 board every frame for the whole ~800 ms draw-in" is wrong at source; its 842 ms/s measurement was real but composed of erase + glyphs. Suggested corrections-ledger line: *L28 F1 root cause "draw-in phase filtered" → the draw-in was never filtered; erase phase + per-glyph reveal draw-ins carry the transition grain re-raster.*

**Caveats, fail-explicit:**
- **The 133 ms-class @4× worst frame is NOT cut.** It was never raster: F1's *second* root cause (synchronous `generateGridBoilFrames` + 256 `wobbleRect` cell-ghost regen + 256 cell/glyph mounts + 300 ms-class style recalc) is main-thread work this hoist does not touch and P3 never booked. Anyone reading D22 as "the hoist fixes the 4× hitch" will be disappointed — that needs a CPU lever (memoized/idle-chunked path regen), a fresh ledger candidate for W5-or-later.
- 4× busy% +4.7 pp consistent: same fixed main-thread work over a similar wall plus ~150 extra one-shot `filter`-attribute patches at glyph completion; no cadence cost (>28/>45 counts identical). Desktop busy is a wash and desktop jank improves.
- After-side raster (~389 ms/s over the ~1.3 s window ≈ 500 ms total) is legitimate one-shot paint: the new geometry must raster at least once + 4 steady-layer prebakes + settled glyph rasters.

## Visual regression — soul gate

- **Settled-board SSIM (the gate's spot check): cross-build max = 1.000** (5 pairs at 1.0 to 5 dp). Method: identical 16×16 board injected via `sudoku-board-state` localStorage into both builds, 10 shots per side across the 4-frame boil cycle, full-board crop 1480×1480 @DPR2, structural SSIM grayscale, all 100 pairs. Cross-build distribution (median .98493 / min .97471) is **identical** to the before/before self-distribution — every sub-1.0 pair is boil-frame mismatch, present in the unpatched build alike. The settled board is pixel-identical; steady layers untouched by construction.
- **Mid-transition, my eyes** (`p3-shots/mid-{before,after}-t{0110,0280,0550,0900,1400}.png`; random boards each side, character judgment): the erase (t0110) and draw-in/reveal (t0280–0900) read identically — the hand-drawn soul lives in the baked path geometry (kinks, wobble, round caps), and the grain tooth is sub-threshold on moving strokes at DPR2. t1400 confirms the tooth lands with the steady swap exactly as before; no visible per-glyph pop (displacement scale 2.5 on a ~46 px glyph). The erase was the only phase that *lost* a filter it visibly had, and it is a 150 ms + 4 ms·i "fast and careless" exit (design §1.2) — symmetric with the draw-in, which was already unfiltered at HEAD.
- The escape hatch (`pencilConfig.ts:170-189` geometric bake) was **not needed**; it stays booked, untouched.

## GATE VERDICT: **PASS**

Material raster cut (−60% desktop / −50% @4×, stable across interleaved replicates) + no visual regression (settled SSIM 1.000; mid-motion character intact by eye). The consuming wave is **T2-W5** ("transition-layer grain-hoist IF P3 clears"); re-apply `pass2/p3.diff` onto the W5 base. W5's own gate should re-trace size-switch (this file's numbers are the template) and note the residual @4× CPU tail as out-of-scope-by-design.

## Deviations

1. The mechanism was extended beyond HandDrawnGrid's transition `<g>` to the per-glyph reveal draw-in — forced by the source finding that the grid draw-in was already unfiltered at HEAD (F1's narrative error); without the glyph half the 4× cut would be ~nil. Both edits are the same F1 discipline ("no filter while the d/dash is morphing"), and F3 explicitly endorses the glyph lever. Side effect (unmeasured here, directionally favorable): solve-celebration beat-1 draw-ins also stop paying per-frame filtered raster; beat-2 flourish (d-morph under filter) deliberately untouched — that's F3's own DEFER, not P3.
2. Decomposition run is single-replicate (attribution only, not a gate number).
3. Worktree `wt-p3` removed after exporting `p3.diff`, `p3-evidence/`, `p3-shots/` — builds are reproducible from HEAD + diff.
