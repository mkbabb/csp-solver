## 4. Findings — two build-breaking incompatibilities, both fixed

### Finding 1 — `esbuild` becomes an optional peer dep; worker bundling needs it explicitly

Vite 8 drops its hard dependency on `esbuild` (Rolldown/oxc replace it for the
default pipeline) and lists it as an **optional peer dependency**
(`^0.27.0 || ^0.28.0`). But Vite's own `vite:esbuild-transpile` plugin — the
code path that bundles the Worker entry graphs — still calls
`transformWithEsbuild` internally. With `esbuild` absent from `node_modules`,
**both** `src/games/sudoku/solver.worker.ts` and
`src/games/futoshiki/solver.worker.ts` fail to bundle:

```
[plugin vite:worker-import-meta-url] .../futoshiki/composables/useSolver.ts
Error: Failed to load `transformWithEsbuild`. It is deprecated and it now
requires esbuild to be installed separately.
Caused by: Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'esbuild'
```

This hit **both games' workers identically** — exactly the surface named in
the task. Fix: add `esbuild@^0.28.1` as an explicit devDependency (the
documented Vite 8 migration step). Confirmed this is not tied to the
`build.minify: 'esbuild'` build option — the failure is in worker-entry
transpilation, a separate internal code path Vite 8 still routes through
esbuild regardless of the minifier setting.

### Finding 2 — `rollupOptions.output.manualChunks` object form is a hard error under Rolldown

`vite.config.ts` used the classic Rollup object-literal form:

```ts
manualChunks: { 'vue-vendor': ['vue'], 'animation-vendor': ['@mkbabb/pencil-boil'] }
```

Rolldown's binding rejects this outright:

```
TypeError: manualChunks is not a function
```

(A non-fatal warning — `Invalid type: Expected Function but received Object`
— prints first but the build only dies once rendering reaches that option.)
Fix: rewrite to the function form, `manualChunks(id) { ... }` — Rolldown's
only supported shape. Applied in the diff.

**Secondary, non-blocking observation** while fixing #2: the object form's
old semantics were dependency-graph-based (name a package; everything *it*
imports rides along transitively, even across separate npm packages) — the
natural function-form translation is an `id`-substring test, and modern
Vue (3.4+) ships `vue` as a thin re-export shell around
`@vue/runtime-core`/`@vue/runtime-dom`/`@vue/reactivity`/`@vue/shared` as
separate resolvable modules, so matching only `/node_modules/vue/` silently
drops 4/5 of Vue's code into the default chunk. Fixed by matching both
`vue/` and `@vue/` prefixes. **Even with that fix — instrumented and
verified every matched module resolves to the intended bucket name — the
two named output chunks still didn't get the expected 1:1 content split**;
Rolldown's chunk-emission redistributed `@vue/shared`'s code into the
`animation-vendor`-named file rather than `vue-vendor`. This is a bundle
**shape** drift only: the import graph and browser behavior are unaffected
(confirmed by the unchanged e2e pass set, §5), and `manualChunks` here is a
vendor-caching optimization, not a correctness requirement. Flagged as a
residual W1-follow-on cleanup item, not a gate blocker — it does not touch
either named surface (plugin codegen, worker bundling).

tightening `manualChunks` further or dropping it in favor of Rolldown's own
default vendor-splitting heuristics, per the Finding 2 residual.
