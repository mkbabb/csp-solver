## THE BUILD (end-to-end, in `wt-P1/`)

**Format decided — `{"puzzle":{"<pos>":<val>,...}}`, sparse, compact.** Two
candidate shapes were measured against the committed bank:

| shape | bytes | note |
|---|---|---|
| `{"puzzle":{…sparse…}}` (wrapped) | **81,963** | byte-exact to the claim; drop-in for both consumers |
| `{…sparse…}` (bare, no wrapper) | 80,687 | −1,276 B more, but breaks **both** consumers |

The **wrapped** form is the correct choice: it reproduces the claimed 81,963 B
*and* is a zero-logic-change drop-in for both readers (see BLAST RADIUS). Verify-11's
`full_compact_sparse` = 81,963 is the wrapped form (`puz_compact 117,925 + 11 B
wrapper ×116 = 119,201` was the *dense* wrapped baseline; stripping the 5,151
zero-holes takes wrapped-dense → wrapped-sparse = 81,963).

Three edits + one deterministic re-materialization (see `P1-source.diff`, `P1.diff`):

1. **`csp-solver/examples/generate_templates.rs`** — emit `{"puzzle":<sparse>}`
   only. Dropped the `solution` (dense) and `backtracks` fields from the written
   JSON and removed the now-unused `dense_json()` helper. The solution re-solve
   and `measure_difficulty` **still run** each iteration (they *are* the
   solvability/uniqueness gate) and still log to stderr — only serialization
   changed. Doc/schema comment updated.
2. **`csp-solver/src/puzzles/sudoku/generate.rs`** — `parse_puzzle_field`
   **logic unchanged** (it already locates only the `"puzzle"` object; sparse maps
   fall through its zero-init `vec![0u32; total]`). Only its doc-comment schema
   line was corrected. *(The synthesis phrase "parse_puzzle_field adapts" is a
   doc + acceptance-confirmation, not a rewrite — confirmed here.)*
3. **`csp-solver/examples/verify_bank_uniqueness.rs`** (new) — Rust-native
   verify-11 harness: drives `embedded_templates` → `parse_puzzle_field` over the
   compile-time `include_dir!` embed, re-solves every board with
   `max_solutions=2`, asserts exactly one solution. Wheel-free (no maturin).
4. **Bank re-materialization** — all 116 files rewritten to wrapped-sparse-compact
   by `P1-reshape_bank.py` (deterministic transform of the *existing* proven boards,
   not a stochastic regen; preserves each file's nonzero-given set byte-for-byte, so
   every uniqueness proof carries over). The adapted generator was *also* exercised
   (fresh N=2/N=3 boards → byte-schema-identical `{"puzzle":{…}}`, no
   solution/backtracks) to prove the generator path, not just the transform.

## FINDINGS FOR THE CONSUMING WAVE (T2-W4)

1. **Wrapped, not bare.** Keep the `{"puzzle":…}` wrapper. It hits 81,963 B *and*
   is a **zero-logic-change drop-in for both consumers** — the Rust parser
   (`parse_puzzle_field` reads only `"puzzle"`) and the frontend Vite plugin
   (`data.puzzle` into a zero-filled array). Bare `{…}` would save 1,276 B (80,687 B)
   but require editing *both* readers. Not worth it; the wrapper is load-bearing.
2. **`parse_puzzle_field` needs no code change** — only its doc-comment. The reshape
   blast radius on the Rust side is: 1 generator (writer) + 1 doc-comment + the data
   files. No test hard-codes the `solution`/`backtracks` schema (grep-confirmed:
   `"solution"`/`"backtracks"` appear only in the generator + the parser doc-comment,
   never a reader or test).
3. **P1 gate-sufficiency (answers Pass-3 Q5):** `parse_puzzle_field`'s *only* Rust
   caller is `embedded_templates`; the sweep drives it for every (N,diff). The
   template pipeline (`generate_board_with_templates`) consumes that same output.
   `difficulty_parity` does **not** read the bank format (it scans for `Difficulty`
   declarations). The wasm/browser path never calls `parse_puzzle_field` — it takes
   `templates: Vec<u32>` as a param, populated by the Vite plugin, which is the
   consumer exercised in node above. The 116-board sweep + the frontend-parse replica
   together cover every consumer; no wider net needed.
4. **Deterministic vs. regen.** This used a deterministic transform of the committed
   boards to (a) hit the exact 81,963 B claim and (b) keep the proven-correct boards
   so the sweep is a true regression check. A stochastic full regen would produce
   different boards and a different (nearby) byte count and cannot hit 81,963 B — W4
   should re-materialize (run `P1-reshape_bank.py`), not re-generate, unless it
   intends to replace the boards.
5. **N=5 interaction with W4's kill.** The 81,963 B gate number *includes* N=5
   (35,907 B). W4's N=5 excision removes that subtree; the post-kill embed is
   **46,056 B** (N=2/3/4 only). Both numbers recorded per the ask.
