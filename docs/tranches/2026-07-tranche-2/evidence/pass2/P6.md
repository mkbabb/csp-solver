## The question

Can a CI lane give **deterministic instruction-count baselines** for the csp-solver benches?
arm64-macOS cannot run Valgrind (`valgrind not found` locally on the M-series host), so callgrind
counts are only obtainable in Linux CI — a CI spike is the only way to know.

## The gate

**Green CI lane + instruction counts stable across 2 runs (<1% delta).**

## The build

One bench, iai-callgrind under Linux/Valgrind. Self-contained — no external service, no token.

- **Bench** `csp-solver/benches/iai_queens.rs` — a single `#[library_benchmark]`, `queens_first_8`:
  build the 8-queens CSP, solve first-solution under `Pruning::Ac3` + `Ordering::FailFirst`
  (`black_box`-wrapped). Fully deterministic workload; exercises the AllDifferent/GAC + AC-3 path.
- **Cargo** `csp-solver/Cargo.toml` — `iai-callgrind = "0.16.1"` dev-dep (latest stable per crates.io
  sparse index) + `[[bench]] name = "iai_queens", harness = false`. Compiles clean locally
  (`cargo build --bench iai_queens`, iai-callgrind-macros 0.6.1).
- **Workflow** `.github/workflows/iai-spike.yml` — scoped to the `spike/iai-callgrind` branch only
  (never master/PRs). `ubuntu-latest`: nightly toolchain → `apt install valgrind` (3.22.0) →
  `cargo install iai-callgrind-runner --version 0.16.1 --locked` (cached in `~/.cargo/bin`) →
  run the bench **twice** → parse `Instructions:` from each run, assert `<1%` run-to-run delta →
  upload logs + `target/iai/**` as artifacts. `IAI_CALLGRIND_COLOR=never` + ANSI-stripping,
  label-anchored parser (see the correction below).

## Gate verdict — **PASS**

Green lane (3/3 runs `success`) **and** instruction counts stable across runs (0.000000% delta,
well under the 1% band). The prototype answers YES: a Linux CI lane gives deterministic
instruction-count baselines for these benches. The criterion `--save-baseline` fallback is **not**
needed on iai's account.

## One correction folded (parser bug — caught + fixed in-spike)

Runs 1–2 were green and the counts were genuinely deterministic, but the workflow's *numeric* gate
initially parsed **`90`** — the digits of the grey ANSI escape `\e[90m` — instead of the real
`1585722`, because iai-callgrind emits colour even off a TTY and the first `[0-9]+` on the line was
the colour code. The gate still passed (both runs yielded `90` → 0% delta) and iai's native
`No change` diff already proved determinism, but the machine assertion was checking the wrong token.
Fixed at `ff5d9de3`: `IAI_CALLGRIND_COLOR=never` + `CARGO_TERM_COLOR=never`, ANSI-strip the log,
and anchor the digit-run to the `Instructions:` label. Run 3 confirms the fix (`'1585722'`).
The `P6.diff` artifact is the **post-fix** patch.

## The comparison arm — codspeed-criterion-compat: NOT wired (FAIL-EXPLICIT, by scope)

`codspeed-criterion-compat` (latest 5.0.1) is **not** "quick": its instrumentation is uploaded by
`CodSpeedHQ/action`, which requires the **CodSpeed GitHub App installed on the repo** + a
`CODSPEED_TOKEN` repo secret. Neither is installable from this seat, and a self-contained spike
cannot provision an external SaaS integration. Deliberately left out — the iai-callgrind arm alone
clears the gate and is the arm the wave actually consumes (no third-party service dependency). If the
wave wants the codspeed comparison, it is a separate owner action: install the app, add the secret,
then a `CodSpeedHQ/action@v3` step running `cargo codspeed` over a criterion-compat bench.

Re-apply `P6.diff` (the 4-file patch: workflow + bench + Cargo.toml + Cargo.lock — Cargo.lock
regenerates via `cargo build` if preferred). The `spike/iai-callgrind` branch is left on origin for
reuse. Notes for productionizing:
- The lane is **branch-scoped** (`on.push.branches: [spike/iai-callgrind]`). To gate master, move the
  bench to the main `ci.yml` and add a threshold policy — but iai deltas are exact, so a strict
  `--fail-... ` policy is only meaningful across *compiler/code* changes, not run-to-run noise (there
  is none). The natural W3 use is a **committed baseline** compared per-PR, not a per-run stability check.
- Runner/library versions are pinned in lockstep (`0.16.1` both). Bump them together.
- Valgrind is `apt`-installed (~15s) and the runner is `cargo install`-cached; warm runs are ~2 min.
- iai-callgrind is a **dev-dependency** and the bench is Linux/CI-only — it never touches the wheel,
  the wasm artifact, or arm64-macOS local `cargo test`/`cargo bench` (which skip `--bench iai_queens`
  unless explicitly named, and would fail-fast with a clear "valgrind not found" if it were).
