## THE QUESTION

What does BANK-LESS sudoku generation cost *in the browser*, off the main thread,
at N=2 and N=3 across all three difficulty tiers? Every native gen timing in L11
is native (verify-11 §7); L27 measured wasm *solve*, not *gen*. The P2 row predicts
a browser multiplier of ~1.8× over native and asks whether p95 clears a felt-latency
budget of **≤50 ms**. Clearing it is what lets W4 delete the N=2/N=3 template banks
and route those sizes to live wasm hole-dig generation.

"Bank-less" = `generateSudoku(n, difficulty, seed, EMPTY)` with an **empty**
templates buffer, which forces the hole-dig slow path in
`csp-solver/src/puzzles/sudoku/generate.rs::generate_board_slow_with_rng`: seed a
Latin square (shuffle first row + AC-3/FailFirst solve), then random hole-dig with a
`max_solutions=2` uniqueness check per removed cell. This is exactly the path a
user hits when a size's bank is absent — `useSolver.ts:119` resolves
`TEMPLATE_BANK[size]?.[key] ?? []` to `[]`, making an empty `Uint32Array`
(`:121`), which the worker hands to `generateSudoku` as empty templates.

## THE BUILD

Browser harness — Playwright (Chromium 145 headless) driving a **module Web
Worker** that loads the **lean** wasm artifact and mirrors the production
off-main-thread path (`src/games/sudoku/solver.worker.ts`).

- **Artifact:** the shipped lean deploy build, `csp-solver/wasm/pkg/csp_solver_wasm_bg.wasm`,
  **87,853 B**, sha256 `03bcbbc2…59be5`. Verified lean (`--no-default-features`):
  export surface is exactly `{init, generateSudoku, generateFutoshiki, solveSudoku,
  solveFutoshiki}` — no `assignment`/`isomorphic` symbols. 87,853 B is the
  ledger-corrected lean-z size (D21 / verify-27, rebuilt-fresh byte-exact); the pkg
  is gitignored build output, HEAD-faithful per D24's content-hash match. Copied
  byte-identical into the harness (sha match confirmed).
- **Worker** (`P2-harness/bench.worker.js`): `import init, { generateSudoku }`,
  `init({module_or_path: …bg.wasm})`, then per request times
  `performance.now()` strictly around `generateSudoku(n, diff, seed, EMPTY)`,
  transfers the board buffer back. Same import-by-URL + transferable-board shape as
  the real worker.
- **Driver** (`P2-harness/index.html` + `run.mjs` + `server.mjs`): page spawns the
  module worker, drives 6 tiers sequentially — **3 warmup (discarded) + 25 timed**
  gens each, fresh varying seed per gen (`Date.now()`-class entropy, matching
  `useSolver.ts:131`). Records per-gen compute (worker) and round-trip (page).
  Static server sets `application/wasm` for streaming instantiation.
- **Host:** Apple Silicon (M5 Max class, `hardwareConcurrency=18`), HeadlessChrome
  145.0.7632.6. Same hardware class as verify-11's native box → the native↔wasm
  ratio is a clean same-machine multiplier, not a cross-host confound.

Harness files: `P2-harness/{bench.worker.js,index.html,server.mjs,run.mjs,pkg/}`.
Raw output: `P2-harness/result-run{1,2,3}.json`. Reproduce:

## THE MEASUREMENT

Pure compute (ms), `generateSudoku` with empty templates, 25 timed gens/tier,
3 independent harness runs. p95 column = worst p95 across the 3 runs (conservative).

| Tier | given/cells | compute p50 | compute p95 (worst of 3) | compute max | round-trip p95 |
|---|---|---|---|---|---|
| N2-easy   | 12/16 | 0.10 | **0.20** | 0.20 | 0.20 |
| N2-medium |  7/16 | 0.10 | **0.30** | 0.40 | 0.30 |
| N2-hard   |  4/16 | 0.20 | **0.38** | 0.60 | 0.38 |
| N3-easy   | 61/81 | 2.50 | **2.98** | 3.10 | 3.00 |
| N3-medium | 35/81 | 5.60–5.80 | **6.84** | 7.20 | 6.44 |
| N3-hard   | 23/81 | 19.6–19.8 | **23.98** | 27.90 | 23.86 |

p50 is rock-stable across all 3 runs (N3-hard p50 = 19.6/19.8/19.7). Round-trip
(page-observed post→receive, incl. thread hop + transferable clone) tracks compute
within <0.4 ms everywhere — the worker boundary adds nothing felt.

**Given-fraction sanity** confirms the genuine hole-dig path (not a stub): measured
givens N2 0.75/0.44/0.25, N3 0.75/0.43/0.28 reproduce verify-11 §8's native
given-fractions (N2 0.750/0.438/0.263, N3 0.753/0.432/0.301) to within the
stochastic-dig wobble on the hard tiers. The wasm is producing correctly-graded
boards, seed-for-seed.

~1.5–2.3× (p95), consistent across tiers.

### Which tiers clear — stated plainly (the W4 input)

- **N=2 — all tiers: EXCISE-SAFE, unconditional.** p95 ≤ 0.38 ms, ≥132× headroom.
  No plausible device slowdown reaches 50 ms. (verify-11: the N=2 bank is only
  9,239 B raw — small embed win, but zero risk.)
- **N=3-easy, N=3-medium: EXCISE-SAFE.** p95 2.98 / 6.84 ms, 7–17× headroom;
  robust to any realistic low-power-mobile multiplier (a 5× penalty still clears
  N3-medium at ~34 ms).
- **N=3-hard: CLEARS on the reference machine (p95 24 ms, 2.1× headroom) — but this
  is the one device-sensitive tier.** Per the synthesis §4 environment-bound-ms rule,
  the 50 ms budget must hold on real user hardware, not just this M-class desktop.
  A ~2× low-power-mobile slowdown still clears (~48 ms); a ~3× slowdown busts (~72 ms).
  *[corrected at W7 — two claims here fail verify-P1-P2: (1) "N=3-hard is where the
  N=3 embed savings mostly live" is struck — that 77,062 B is the **dense** bank; on
  the **sparse** embed the per-tier weights invert (easy **8,633 B** > medium 3,036 B
  > hard **3,591 B**), so the device-sensitive tier is the *cheapest* to keep, not the
  savings center. (2) "survives a 2× mobile penalty" overstates — under same-desktop
  contention headroom shrinks to ~1.6×, so **≥2× busts**; excise N=3-hard only behind
  a genuine low-power-device confirmation run.]*

**Recommendation to W4:** excise the N=2 and N=3 banks and route both to bank-less
live-gen (the P2.diff below). Treat N=3-hard as the single sensitivity point: if the
tranche wants zero mobile risk, gate N=3-hard's excision behind one confirmation
run on a genuine low-power device (a ~3×+ slowdown is the only thing that busts it),
or keep just the N=3-hard bank while excising N=2 + N=3-easy/medium. N=4 stays banked
regardless (verify-11: >1 s native hard wall — outside this prototype's scope).

## SCOPE / CAVEATS

- **One-time wasm init** (~module load) is absorbed by the 3 warmups and is a shared
  worker cost present with or without banks (the worker loads wasm either way) — not
  a differential cost of the bank-excision decision, so out of gate scope.
- All ms are regimes/ratios per the 30-repro rule; the desktop↔mobile factor above
  is the honest uncertainty, flagged not hidden.
- The prototype measured the *shipped* lean artifact (most honest — it's what users
  run). Not independently rebuilt here; HEAD-faithfulness rests on the D24/verify-27
  byte/hash chain.
