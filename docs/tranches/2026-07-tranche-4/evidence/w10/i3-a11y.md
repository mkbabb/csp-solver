## GATE 2 — FOCUS RING THAT SURVIVES FORCED-COLORS (WCAG 2.4.7; T3-W9 §3.2, crayon-blue not gold)

**Born-RED (C3):** the board cell `<input>` carries Tailwind v4 `outline-none` (compiles to
`outline-style:none` — paints nothing), and forced-color-adjust strips the SVG `.cell-ghost-path`
to a corner fragment; the `SudokuCell:698` comment's "transparent 2px outline HC repaints" premise
is stale v3 behavior. **Correction to C3's lever:** C3 proposed `.cell-native-input:focus-visible
{ outline }`, but the input is `opacity-0` — an opacity-0 element renders **no** outline (opacity
hides it). So the HC ring rides the **cell** (opacity 1), gated on the input's `:focus-visible`:

```css
@media (forced-colors: active) {
  .sudoku-cell:has(input:focus-visible)   { outline: 2px solid Highlight; outline-offset: -2px }
  .futoshiki-cell:has(input:focus-visible){ outline: 2px solid Highlight; outline-offset: -2px }
}
```

System `Highlight` (the UA forces its own palette under forced-colors — crayon-blue is unrenderable
there; never gold). Inset (`-2px`) so the ring hugs the packed cell without overlapping neighbours.
Gated on `:focus-visible` → keyboard only, matching the normal-mode ghost. The stale premise at
`SudokuCell:696-702` and `FutoshikiCell:675` is corrected in place; **normal mode is untouched**
(the SVG ghost stays the crayon-blue ring — captures AE=0).

**Measured (`i3-focus.mjs`, `forcedColors:'active'`, both games, both schemes):**

| context | cell outline (computed) | ring |
|---|---|---|
| normal light (both games) | `…none…` (SVG ghost is the ring) | unchanged |
| forced-colors LIGHT | `2px solid rgba(5,0,73,0.8)` off -2px | **visible full ring** |
| forced-colors DARK | `2px solid rgba(0,230,255,0.8)` off -2px | **visible full ring** |

The HC colors are Chromium's emulated palette — the same `rgba(5,0,73,0.8)` the surviving chrome
controls repaint to (C3). π: `i3-focus-{sudoku,futoshiki}-forcedcolors-{light,dark}.png` show a
full rectangular ring on the focused cell (vs C3's `focus-cell-forcedcolors-*.png` corner fragment).
`input.matches(':focus-visible')=true` under programmatic focus (text-input heuristic), so the
`:has()` selector fires; input `outline-style` stays `none` (WM-frozen shape untouched).

Recipe: `BASE=http://localhost:4490 node i3-focus.mjs`

attribution is wrong** — the driver probe (`i3-reflow-probe.mjs`, dumps each offender's computed
`min-width`/`width`) shows the futoshiki board-shell is **296px and fits**; the 331.9px overflow
is the **wordmark logo**:

```
futoshiki @320: logo-trigger 331.9 = handwritten-logo svg 301.5 + gap 0.4rem(6.4) + caret 1.5rem(24)
```

`.board-group` has `min-width:auto`, so it grows to the masthead/logo min-content (331.9) and
overruns the 320 viewport by 5.9px (the "futoshiki" wordmark is 9 glyphs — sudoku's fits, hence
sudoku clean @320). The board never was the driver. **Fix:** a narrow-phone rung on the existing
`--logo-height` ladder (`HandwrittenLogo.vue`) — below **360px** the wordmark steps one rung down
so wordmark+caret clears the viewport, proportional (caret + optical nudge ride `--logo-height`),
never letterboxed, never a glyph-shrink hack:

```css
@media (max-width: 360px) { .logo-menu { --caret-size: 1.3rem; --logo-height: 3.9rem } }
```

Scoped ≤360px, so 375 / iPhone-13 390 / desktop 1280 are untouched (no capture or golden at those

## GATE 4 — TARGET SIZE (WCAG 2.5.5 AAA 44px / 2.5.8 AA 24px)

**Re-measured on the merged dist (`c3-rt2.mjs` → :4490); identical to C3 — my fixes touch no
board geometry, so no regression.** Representative (bulk) cell; the transient grid-collapse
cells (0×0 / sub-px, `zeroInput` 11–14 of 256 at 16×16) are the measurement artifact C3 flagged,
excluded from the representative figure.

| board | @390 | @320 | vs 44 (AAA) | vs 24 (AA) |
|---|---|---|---|---|
| **futoshiki 5×5** | 72.39 | 58.39 | **PASS both** | PASS both |
| **sudoku 9×9** | 40.22 | 32.44 | FAIL both | **PASS both** |
| **sudoku 16×16** | 22.63 | 18.25 | FAIL both | **FAIL both** |

**The honest read (C3's, re-confirmed): 44px AAA is geometrically impossible for a packed N×N
grid at these widths — 9×44=396 and 16×44=704 both exceed 320/390, and the input already fills
the cell edge-to-edge, so hit-area cannot extend without overlapping neighbours (C3).** The only
lever is board width, and board width is capped by the viewport. The three constraints on this
lane forbid every path that would cross the threshold:
- **glyph-shrink** — banned by the gate ("never glyph size");
- **horizontal-scrolling board** (the C3 lever for a min-cell floor) — would **re-break gate 3**;
- **desktop board-geometry change** — the goldens capture the board at 1280 (42rem), so any
  padding/width reclaim that reached desktop **moves goldens**.

So the achievable floor is **AA 24px, not AAA 44px, for 9×9/16×16** — the exact conclusion C3
reached. `index.css:671-677` already codifies the board-cell exemption from the coarse 44px floor
on this arithmetic ground (**D12**); it is the WCAG 2.5.5/2.5.8 *essential-presentation* exception
made explicit. **futoshiki 5×5 meets AAA 44; sudoku 9×9 meets AA 24 (44 capped); sudoku 16×16 is
sub-24 below ~408px viewport** (16×24=384 board unreachable under ~408 without a scrolling board)
— an irreducible density case governed by D12. No golden-safe / gate-3-safe / glyph-safe code
change moves any of these figures, so this gate closes as a **documented geometric cap +
verified existing exemption**, not a silent pass. Recipe: `node c3-rt2.mjs` (BASE → :4490).
