## Findings

### F1 (P2) — Light-mode "Difficulty" section heading fails WCAG 1.4.3 AA (Easy 2.22:1, Medium 2.05:1)
family_hint: `crayon-as-heading-text-contrast`

The Difficulty `<h2 class="section-heading">` recolors its TEXT to the selected difficulty's raw
crayon via `.crayon-green` / `.crayon-orange` / `.crayon-rose`
(sudoku/ControlPanel/ControlPanel.vue:211-217 mobile, :350-356 desktop; classes at :489-496 set
`color: var(--color-crayon-*)`). In light mode on the near-white panel (`rgb(253,253,252)`) the
25.9px heading measures:
- Easy  → `#2DC653` green  = **2.22:1** (FAIL — large-text floor is 3.0)
- Medium→ `#F4A236` orange = **2.05:1** (FAIL)
- Hard  → `#E8315B` rose   = 4.11:1 (pass)

Dark mode passes all three (crayons brighten to 6.3–10.2:1). This directly contradicts the
palette's own ledger, which states crayons are unfit as light-mode text:
index.css:151 — "Every crayon fails AA as light-mode text (green ...)". The ink-tier tokens
(`--color-gold-ink` etc, darkened for AA) exist precisely for this, but the heading uses the raw
crayon, not an ink token.

Live trigger: default light theme, click Easy or Medium (both default-reachable). Evidence:
`probes/heading-diff.cjs` (all 6 states measured), visual `probes/shot-difficulty-easy-light.png`
(green DIFFICULTY on white). The `.crayon-rose` state ships as the visible default in my run, so
the failing states are one click away.

### F2 (P3) — `outline-none` comment describes Tailwind v3 behavior the v4 upgrade silently broke; forced-colors focus fallback does not exist
family_hint: `tailwind-v4-outline-none-rename`

SudokuCell.vue:394 (and the identical FutoshikiCell.vue:193 markup) claims: the board-cell input
"keeps Tailwind's `outline-none` (a transparent 2px outline) so forced-colors / Windows High
Contrast still paints its own visible ring where SVG strokes are ignored."

That is false under Tailwind v4 (this repo, `tailwindcss ^4.3.2`). The compiled utility is
`dist/assets/index-QARPYg8w.css` → `.outline-none{--tw-outline-style:none;outline-style:none}` —
`outline-style:none`, NOT a transparent 2px outline. (Tailwind v4 renamed the v3 transparent-
outline behavior to `outline-hidden`; `outline-none` now zeroes the style.) Confirmed at runtime:
the focused cell input computes `outline-style: none` under both normal and `forcedColors:active`
(`probes/forced-colors-focus.cjs`).

So the stated forced-colors safeguard is absent. The only focus affordance on board cells is the
crayon-blue SVG ghost path (`.cell-ghost-path`, SudokuCell.vue:348-356). Whether that ghost
survives forced-colors is uncertain (getComputedStyle returns authored values, not the paint-time
forced-color override, so I could not prove it either way — `probes/fc-ghost.cjs`). Net: a
provable stale/false code comment about an a11y safeguard that the build output disproves, with a
plausible-but-unconfirmed forced-colors focus-visibility gap behind it. In normal mode the ghost
ring is present and visible, so no regression for the common case.

### F3 (P3) — Futoshiki overflows the viewport by 6px at 320px (WCAG 1.4.10 reflow)
family_hint: `reflow-overflow-narrow`

At a 320 CSS-px viewport the futoshiki scene produces `scrollWidth 326 > clientWidth 320` → a 6px
horizontal scrollbar; widest overflower is `DIV.board-group` (right=326). Sudoku is clean at 320
(scrollWidth 320, overflow 0); futoshiki is clean at 375. So the futoshiki board's min-size floor
doesn't quite fit the 320px reflow target. Probe: `probes/mobile-reflow.cjs futoshiki`.

### F4 (P3) — Sudoku 9×9 board cells drop below the project's stated 44px touch floor on narrow screens
family_hint: `board-cell-target-size`

At 375px the 9×9 cells render 39×39px; at 320px, 32×32px (`probes/mobile-reflow.cjs sudoku`; the
81 sub-44 targets are exactly the 81 board cells — every real control button meets 44px). This
passes WCAG 2.5.8 AA (24px floor, and adjacent same-purpose cells qualify for the spacing
exception) but misses the 44px floor the project asserts elsewhere (DrawerTab.vue:11 "48×92px ≥
the 44px floor"). Inherent to fitting 9 columns into 320px (9×44=396 > 320); noted as a bounded
gap between the stated floor and the board reality, not a WCAG-AA failure.
