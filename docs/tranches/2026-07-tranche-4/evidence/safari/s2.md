# LANE s2 — WebKit filter-caching mechanics, proven by injection

**Verdict, one line:** WebKit does **not** cache a filtered-SVG raster across visibility
*or* opacity flips — it re-executes the whole `feTurbulence`+`feDisplacementMap` chain on
the CPU **every flip**. The pose-stack boil architecture (frozen filter per pose, flip the
beat) is Chrome-shaped: it assumes exactly the raster cache WebKit lacks. On the real dist
in WebKit this pins **one full CPU core at idle** (100%), of which **97.3% is filter
raster** — proven by injection (`filter:none` collapses idle 100%→2.7% while the beat keeps
flipping).

All numbers first-party, this machine (`darwin 25.4.0`), playwright webkit-2311 /
chromium-1228, headless, **DPR 1** (real retina Safari renders at DPR 2 → raster area ×4,
so absolute costs below are a *floor*). CPU = summed `top -l 2` interval CPU% over the
`ms-playwright/<engine>` process tree, isolated per case (one fresh browser, pkill+settle to
a clean slate between every case — `pids=5`/`4` confirms no cross-contamination). Recipes are
rerunnable beside this file in `s2-fixtures/`.

### The five answers the lane was asked to prove

1. **Cache across visibility flips? NO.** `static_logo` 0% vs `flipVis_logo` 5.6% — WebKit
   re-rasters the frozen filter on every visibility flip. A raster that Chrome does once and
   composites, WebKit redoes 8×/s.

2. **Opacity flips + will-change? WORSE, and inverted vs Chrome.** Opacity+`will-change:opacity`
   — the *exact production config* of the logo/toggle pose stacks — costs **9.8%** in WebKit
   (the single most expensive case) but **0.5%** in Chromium. `will-change` *promotes the
   filtered layer to a cached composited texture in Chrome* (raster once, flip = compositor
   blend → 0.6 ms) and *makes WebKit worse* (9.8 vs 5.3 without it): the promotion WebKit
   performs re-rasters the filter into the layer per flip. **The optimization that makes the
   boil free in Chrome is the one that makes it most expensive in WebKit — a 20× gap on the
   same DOM.**

3. **Cost of ONE turbulence+displacement raster (WebKit, DPR 1):** ~2.0 ms @ 208 px toggle,
   ~7.0 ms @ 734×238 logo, ~7.4 ms @ 400×400 region. Scales ~linearly with filter-region area
   (~0.043 ms per 1000 px²). Chromium's *visibility*-flip raster is comparable (1.8–6.5 ms) —
   WebKit is not slower *per raster*; it just **rasters when it shouldn't have to.** At retina
   DPR 2 every figure ×~4 (logo ≈ 28 ms/raster).

4. **The pose-stack multiplier at REST: zero.** 1, 4, and 12 resident frozen-filter siblings,
   all visible, no flipping → **0% in both engines**. WebKit pays **nothing** for resident
   filtered DOM at rest. The entire cost is in the *flip*, not the sibling count. (So stacking
   N poses is free; driving the beat is what burns.)

5. **The scheduler is healthy in WebKit.** pencil-boil 0.8.1's parked beat on the real dist:
   `setInterval` calls = **0** (no interval runaway), every `setTimeout` delay = **125 ms**
   exactly (histogram `{125: 188}`), rAF is beat-tied (18.8/s), **not** a free-running 60/s
   rAF loop. The scheduler parks correctly. **The scheduler is not the problem — what it
   drives is:** each 125 ms beat flips filtered content, and each flip re-rasters.

## Ground-truth on the real dist (the headline number)

`dist-ab.mjs` on `http://localhost:4188/` (fresh build 65425697 tree, WebKit, DPR 1):

| state                                             | idle CPU% |
|---------------------------------------------------|:---------:|
| **A — boils live (as shipped)**                   | **100**   |
| B — `filter:none` injected, beat still flipping   | **2.7**   |
| C — all timers cleared                            | 0         |

- 63 elements carry a live `url()` SVG filter on first paint.
- **Filter-raster attribution = 97.3%** (A−B). Neutralize the filters and the beat/opacity
  machinery costs 2.7%; the timers themselves cost ~0. **Essentially all of WebKit's
  one-core-pinned idle is SVG-filter re-raster driven by the pose-stack beats.**
- Cross-checked by `scheduler.mjs`: 112% idle in that run (one WebContent renderer at 110%),
  same core-pinned regime. Chrome's certified idle on this tree is 0 recurring Paint / 7.99
  fps — free.

## What s3's design must stand on

- **Zero-cost WebKit states, measured:** (a) a static filter that rasters once and is *never*
  flipped; (b) resident filtered siblings that never change visibility/opacity. Anything that
  flips filtered content re-rasters, period.
- **`will-change:opacity` on filtered content is a WebKit anti-pattern** (9.8 vs 5.3). It is
  load-bearing for Chrome's free path and actively harmful in WebKit — it cannot be tuned to
  satisfy both; the *architecture* has to change, not a property.
- **The fix shape is already in this codebase.** The grain hoist (pre-rastered filter layers,
  opacity-swap) and the stroke boils (displacement baked into path geometry) are exactly the
  two zero-live-filter disciplines that measured 0% here. Extending either to the wobble
  surfaces — pre-raster each pose to a bitmap/`<image>`/canvas and swap the *bitmap* (no live
  filter), or bake the per-pose displacement into path `d` — removes the re-raster while
  preserving the identical frozen-pose frames. Both keep the boil's look byte-for-byte; they
  only move the filter out of the steady-state raster path.
- **Resident stacks stay free** — no need to reduce pose count or unmount siblings; the lever
  is purely "don't drive a live filter on the beat."
