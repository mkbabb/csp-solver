# Lane s3 (design) — the zero-compromise WebKit fix: bitmap pose cache

**Owner verdict:** *"The performance in safari is god awful and nearly entirely
unusable. What pencil-boil facilities might we change—without a compromise in
quality and design in any way. Profile."*

**Answer:** the per-beat opacity flip of **resident filter-bound SVG siblings** is the
whole cost. WebKit re-executes the `feTurbulence + feDisplacementMap` chain in the GPU
process on every flip (it does not cache the filtered raster across opacity changes,
unlike Chrome). **Fix: capture each frozen pose to an `ImageBitmap` ONCE at mount and
swap bitmaps on the beat — no resident filter.** The rendered pixels are the filter's
own output, captured, so identity is exact (SSIM 1.0000 by construction, not a
re-derivation). Ship it as a new pencil-boil facility, `useRasterStack` (0.9.0),
**unified across both engines** (it also erases Chrome's residual ~8/s tile churn).

Rig: dist build of `65425697` (my `npm run build`), served by `vite preview` on a
private `:4319` (owner's `:3001` and the sibling lanes' `:4317` untouched). Driven by
`playwright.webkit` (Apple WebKit-2311 — the Safari engine) at DPR2. No CDP in WebKit:
every number below is a first-party in-page rAF/timer probe, a macOS `/usr/bin/sample`
of the WebContent process, or a `ps` CPU sample. Recipes are rerunnable beside this
file (see §Recipes).

## 1. Profiling — the mechanism, first-party (corroborates lane s1)

### 1a. The cost is filter EXECUTION, not the opacity swap or the layer count

Surface-isolation A/B, headless WebKit, DPR2, 8 s idle windows. The decisive pair:
null **only** the `filter` (DOM kept, all four pose siblings kept, the opacity swap
kept) vs the shipped resident filter. `probe-webkit.mjs`, first clean sweep:

| condition | WebContent CPU mean | CPU max | dropped frames (>20ms) | Δmax (ms) |
|---|---|---|---|---|
| **baseline** (all boil resident) | **11.9%** | **106.8%** (a pegged core) | 17 | 45 |
| `nofilter-grid` (filter:none, DOM+opacity kept) | 2.6% | 3.8% | 0 | 19 |
| `nofilter-logo` | 2.4% | 3.0% | 0 | 20 |
| `hide-grid` (display:none) | 3.5% | 24% | 0 | 18 |
| `hide-celestial` | 2.6% | 3.4% | 0 | 18 |

Nulling the filter while keeping the exact DOM, the four `will-change:opacity` layers,
and the 8 Hz opacity flip collapses the cost to the floor — **identical to hiding the
surface outright.** So the frozen-pose *stack* (siblings + opacity swap) is not the
problem; the resident **filter re-execution on the flip** is the entire problem.

### 1b. The work runs in the GPU/compositor process, not JS

`/usr/bin/sample` of the WebContent render process during baseline idle
(`sample-baseline.txt`): the main thread is **6275 / 6337 samples parked in
`mach_msg`** (idle wait); the paint that does occur threads through
`RemoteLayerBackingStoreCollection::paintReachableBackingStoreContents →
createContextAndPaintContents → drawLayerContents`, and `CoreImage` symbols appear in
the stack. The filter rasterizes through **CoreImage on WebKit's RemoteRendering
(GPU) path.**

GPU-process attribution (`probe-gpu.mjs`, baseline row, uncontaminated moment):
idle **GPU process 11.2% mean vs WebContent 2.8%** — the boil cost lives in the GPU
process, not the main thread. (My cross-condition GPU deltas were contaminated by the
sibling lanes' concurrent WebKit GPU processes — WebKit's XPC processes reparent to
`launchd`, so a `ps` sum over `com.apple.WebKit.GPU` catches every lane's browser at
once; lane s1's pre-launch baseline-diff is the clean absolute number.)

### 1c. Headless understated the SEVERITY; the mechanism is the same

My headless rAF held ~60 fps because offscreen WebKit rasterizes on a path that does
not saturate the way real Safari.app's on-screen compositor does. **Lane s1's real
Safari.app measurement is the representative severity** and independently names the
identical mechanism and culprit:

> *Hiding only the grid grain-hoist (`.boil-frame-layer`) at idle: WebKit GPU process
> 624% → 78% CPU, page 4.6 → 49.6 fps. WebKit does not cache a filtered-SVG raster
> across an opacity/visibility flip — it re-executes the whole feTurbulence +
> feDisplacementMap chain in the GPU process, per flip, and the cost scales with
> filtered AREA. Chrome is a flat 120 fps / ~0% GPU with the identical markup.*
> — `s1.md`

Two independent lanes, two probe methods, one mechanism. The grid is worst because it
is the **largest filtered area** (~board-sized, ≈1200×1200 device px at DPR2), flipped
four-deep at 8 Hz. The logo (~1468×476 device px) is next; the celestial icons
(~160×160) are minor.

**Why the W13 pose-stack architecture backfires in WebKit:** it was built on Chrome's
"raster each frozen-filter sibling once, then compositor-swap" model. That model is
**false in WebKit** — and most false where the filtered area is largest. Correct in
Chrome, a full-core GPU saturation in Safari.

## 2. Self-verify — the bitmap pose cache's identity + taint claim holds in WebKit

The one load-bearing risk of the recommendation is: *can you rasterize a
filter-bound inline SVG to a canvas in WebKit without CORS-tainting it, and is the
capture the same pixels the filter produces?* Fixture `fixture.html` +
`run-fixture.mjs`, WebKit DPR2, four frozen wobble poses (turbulence+displacement),
serialize→`Blob`→`drawImage`→`getImageData` (`results-fixture.txt`):

```
{ "dpr": 2, "allClean": true, "repeatMatch": true, "distinctPoseHashes": 4,
  "poses": [ {"tainted": false, "nonBlank": 77573, "w":480,"h":480}, ... ] }
```

- **`allClean: true`** — `getImageData` did **not** throw on any pose: a same-origin
  inline-SVG serialized to a `Blob` URL and drawn to canvas produces an **untainted**
  canvas. No CORS taint. (The filter `<defs>` must be **inlined into the serialized
  SVG** — a detached blob-URL document cannot reach the page's `<defs>`; the fixture
  does this and stays clean.)
- **`repeatMatch: true`** — rasterizing the same pose twice yields a byte-identical
  pixel hash: the capture is **deterministic**. This is the SSIM==1 identity class the
  swap relies on — the bitmap *is* the filter's raster, not an approximation.
- **`distinctPoseHashes: 4`** — the four poses hash distinctly: the filter is genuinely
  applied and each pose differs, so the boil motion is preserved pose-for-pose.

The design's central claim is verified in the target engine at production DPR.

## 3. Ranked facility-change proposal

The absolute constraint: **the rendered pixels and the motion grammar may not change.**
Every candidate is judged against it.

### ✅ #1 — BITMAP POSE CACHE, unified across both engines (RECOMMENDATION)

Rasterize each frozen pose to an `ImageBitmap` once at mount (SVG→Blob→`drawImage` at
device DPR — the same raster the filter would produce, captured). Render the stack as
static bitmap layers (no `filter=`) opacity-swapped on the beat, **or** as a single
`<canvas>` that `drawImage`s the current pose's bitmap per beat. Per-beat cost becomes
one GPU blit of a cached texture in **both** engines — no filter ever re-executes at
steady state.

- **Identity:** exact. The bitmap is `drawImage` of the filter's own output (§2 proof).
  SSIM 1.0000 by construction — stronger than the W13 grain-bake's 0.983–0.996, because
  there is no re-derivation, only a capture.
- **Motion grammar:** unchanged. Same four poses, same shared-beat cadence
  (`useBeatFrame`), same seeds/frequencies (`wobblePoseFrequencies`) — only the paint
  substrate changes (baked pixels instead of a live filter).
- **Erases Chrome's residue too:** Chrome currently opacity-blends four filtered
  compositor layers ~8/s (the W13 audit's residual tile churn); a single-canvas bitmap
  draw makes Chrome's per-beat cost one blit as well. **One architecture, both engines
  faster** — the argument for unify over gating (#2).
- **Where it lives:** a pencil-boil facility (portable; every consumer benefits, and
  the frozen-pose vocabulary — `wobblePoseFrequencies`, `wobblePoseId` — is already
  library-adjacent). New browser-only core `src/raster.ts` + a Vue composable
  `useRasterStack`, memoizing each `ImageBitmap` through the existing `useBoilCache`
  under key `(surfaceId, pose, dpr, theme, size)`. Frontend change is per-surface: swap
  the filtered `<g>`/`<svg>` stack for the composable's bitmap layers/canvas.

**Memory arithmetic (DPR2, RGBA `ImageBitmap`):**

| surface | device px / pose | bytes / pose | poses | subtotal |
|---|---|---|---|---|
| grid (`.boil-frame-layer`) | ~1200×1200 | 5.76 MB | 4 | 23.0 MB |
| logo (`.logo-pose`) | ~1468×476 | 2.80 MB | 4 | 11.2 MB |
| celestial (sun+moon rest) | ~160×160 | 0.10 MB | 4×2 | 0.8 MB |
| **total resident** | | | | **≈35 MB** |

This is not *new* cost — Chrome already holds these as compositor filter-result tiles
(that's why Chrome is fast), and WebKit currently pays it as ~6 cores of per-beat
re-raster. Trading ≈35 MB of explicit `ImageBitmap` residency for erasing 6 GPU cores
is the correct trade. Grid alone (23 MB) captures the dominant win; the stack can bake
grid-only first if a memory ceiling ever bites.

**Startup cost & spreading:** four rasters per surface; each is an async `Image`
decode + `drawImage` (single-digit ms). Bake begins at mount and completes well under
1 s. **Fallback while baking:** render the live filtered pose for the first beat(s) —
one filtered raster per pose *appearance* is the already-sanctioned transient cost
(the L28-F1 "a static filter rasters once per appearance" discipline). Once all four
bitmaps resolve, drop the live filter. No startup jank, no flash.

**DPR / theme / font handling (the three re-bake triggers):**
- **DPR change** (window dragged between monitors): listen
  `matchMedia('(resolution: Ndppx)')` `change`; re-bake at the new ratio, live-filter
  fallback during. Rare, cheap.
- **Theme flip** (light↔dark changes grid-line color, ink, celestial fills): colors
  differ, so re-bake. Serialize with computed color literals (read `getComputedStyle`
  — `currentColor` / `--grid-line-color` must resolve to hex at capture). The theme
  toggle is already the heavy "Bloom" gesture moment, so a re-bake there is masked.
- **Fonts** (logo `<text>` in Fraunces): bake only after `document.fonts.ready`, else
  the bitmap freezes the fallback face. The logo already hooks `fonts.ready`; the bake
  rides the same signal.

### ⛔ #2 — Engine gating (filtered stacks in Chromium, bitmaps in WebKit) — REJECTED in favor of unify

Technically valid — a UA/feature check could keep the live filter on Chrome and bake
on WebKit. Rejected as the primary because: (a) two render paths to maintain and
soul-gate forever; (b) it leaves Chrome's residual ~8/s filtered-layer tile churn on
the table, which the unified bitmap path also erases; (c) UA sniffing is brittle
(Chromium-on-Mac, future WebKit caching changes). Recommend **one path, bitmaps
everywhere.** Keep gating only as the fallback-during-bake seam (§#1), which is a
timing gate, not an engine gate.

### ⛔ #3 — Cheaper stopgaps — REJECTED (they violate the zero-compromise constraint)

Listed to show the space was covered, each a design compromise the owner's "without a
compromise in quality and design in any way" forbids:

| stopgap | what it costs the design | verdict |
|---|---|---|
| Fewer poses (4→2) | halves the boil's stop-motion richness; the shiver reads as a two-frame toggle | REJECTED — motion grammar changed |
| Slower beat (8 Hz → 3–4 Hz) | the boil visibly stutters; "shooting on fours" becomes "on eights" | REJECTED — motion grammar changed |
| Smaller filter margin / lower `numOctaves` | reduces filtered area/cost but softens the grain tooth — a rendered-pixel change | REJECTED — pixels changed |
| Freeze grid boil at one pose in WebKit | kills the grid's idle life on Safari only | REJECTED — design differs per engine |

None survive the constraint. The bitmap cache is the only candidate that removes the
cost while changing **neither** the pixels **nor** the motion.

## 4. Identity-proof plan (release gate for 0.9.0)

1. **pencil-boil proof** `proofs/raster-stack.proof.ts`: assert the §2 invariants
   programmatically — deterministic capture (`repeatMatch`), distinct-per-pose,
   untainted canvas — across each wobble/grain preset. (My `fixture.html` is the seed;
   promote it into the proof harness.)
2. **Frontend soul-gate A/B** (the W13 SSIM discipline, but exact): for each surface
   and each pose, pixel-diff the bitmap-swap render against the shipped filtered-stack
   render at DPR2, settled. Expected **SSIM 1.0000** — the bitmap is the same raster,
   so this is an equality check, not the 0.98 acceptance floor. Any pose < 1.0 means
   the serialization dropped a def (color var, font, filter region) — a bug, not a
   tolerance.
3. **Cross-engine parity:** run the A/B in both Chromium and WebKit — the bitmap render
   must match the *Chrome* filtered reference in both, proving the capture is
   engine-independent (WebKit's filter and Chrome's filter agree at the captured pixel,
   which the distinct-pose hashes already suggest).
4. **Perf regression gate:** re-run lane s1's real-Safari GPU sample on the bitmap
   build — target the grid surface from 624% → single-digit GPU, page 4.6 → ~60 fps,
   and confirm Chrome's residual per-beat tile churn drops to one blit.

## 5. pencil-boil 0.9.0 API sketch

New browser-only core (framework-agnostic — no `vue` import, mirrors `frames.ts`):

```ts
// src/raster.ts
export interface RasterStackOptions {
  /** Stable surface id — the useBoilCache key root. */
  cacheKey: string;
  poseCount: number;
  /** Self-contained SVG markup for pose i: filter <defs> INLINED, colors resolved to
   *  literals, fonts assumed loaded. A detached blob cannot reach the page <defs>. */
  poseSvg: (pose: number) => string;
  /** CSS px the stack renders at; bitmap captured at cssSize * dpr device px. */
  cssSize: { width: number; height: number };
  /** Capture ratio (default devicePixelRatio). */
  dpr?: number;
}

/** Rasterize every pose to an ImageBitmap via same-origin SVG→Blob→drawImage.
 *  Untainted (proven, WebKit DPR2). Each bitmap memoized through useBoilCache under
 *  (cacheKey, pose, dpr, cssSize) so a re-mount / re-theme reuses a warm bake. */
export function rasterizePoseStack(opts: RasterStackOptions): Promise<ImageBitmap[]>;
```

Vue composable (in `vue.ts`, beside `useLineBoil` / `useFilterParamBoil`):

```ts
export interface RasterStackHandle {
  /** null until the bake resolves — render the live-filter fallback while null. */
  bitmaps: Readonly<Ref<ImageBitmap[] | null>>;
  ready: Readonly<Ref<boolean>>;
  /** current pose index, driven by the shared beat (stepEveryBeats forwarded). */
  pose: Readonly<Ref<number>>;
  /** force a re-bake — called on DPR / theme / font-ready change. */
  rebake: () => void;
}

export function useRasterStack(
  opts: MaybeRefOrGetter<RasterStackOptions>,
  stepEveryBeats?: MaybeRefOrGetter<number>,
): RasterStackHandle;
```

Consumer shape (grid, the single-canvas variant — cheapest; drop-in for
`HandDrawnGrid`'s `.boil-frame-layer` stack):

```vue
<canvas ref="boilCanvas" :width="w*dpr" :height="h*dpr" :style="{width:w+'px',height:h+'px'}"/>
<script setup>
const { bitmaps, ready, pose } = useRasterStack(() => ({
  cacheKey: 'grid-' + theme.value, poseCount: 4,
  poseSvg: (f) => serializeGridPose(steadyFrames.value[f], resolvedColors()),
  cssSize: { width: w, height: h },
}))
watchEffect(() => {                       // one drawImage per beat — no filter, no re-raster
  if (!ready.value || !bitmaps.value) return   // else: keep the live-filter fallback stack mounted
  const ctx = boilCanvas.value.getContext('2d')
  ctx.clearRect(0, 0, boilCanvas.value.width, boilCanvas.value.height)
  ctx.drawImage(bitmaps.value[pose.value], 0, 0)
})
</script>
```

Surfaces that want to keep the exact `will-change:opacity` compositor structure
(logo, celestial) use the N-bitmap-layer variant instead: N stacked `<canvas>` (or
`<img>` with the bitmap as a blob URL), `is-active` opacity-swapped on `pose` — same
markup shape as today, `filter=` removed, content baked. Both variants share the one
`useRasterStack` bake.

**Migration:** `SvgFilters.vue`'s frozen `wobble-*-p{i}` / `grain-static` defs stay
(they are the bake SOURCE and the fallback-during-bake filter). `wobblePoseFrequencies`
/ `wobblePoseId` are unchanged. The three consumers (`HandDrawnGrid`, `HandwrittenLogo`,
`DarkModeToggle` rest stacks) swap their resident filtered stacks for `useRasterStack`.
The live gesture instances (the Bloom's warp-wrapped filtered svg) are **untouched** —
they are correctly ephemeral one-shot filter work, not a per-beat resident stack.

## Recipes (rerunnable, beside this file)

- `probe-webkit.mjs [url] [ms]` — surface-isolation A/B sweep (baseline, hide-*,
  nofilter-*, only-*), rAF histogram + `setTimeout(0)` latency + WebContent `ps` CPU.
  `REPEATS=/DPR=` env. Output: `results-dpr2.jsonl`.
- `probe-headed-sample.mjs [url]` — headed WebKit + `/usr/bin/sample` of the busiest
  WebContent pid. Output: `sample-baseline.txt`.
- `probe-gpu.mjs [url]` — GPU-vs-WebContent process split, idle + scroll-storm phases.
  Output: `results-gpu.jsonl`. (Cross-lane GPU contamination noted §1b.)
- `probe-own-gpu2.mjs [url] [repeats]` — pid-pinned own-GPU filter A/B (crash-flaky
  under the shared-machine memory pressure; kept for the method).
- `fixture.html` + `run-fixture.mjs` — the **identity/taint proof** (§2). Output:
  `results-fixture.txt`. This is the recommendation's release-gate seed.

**Environment caveats (first-party):** (1) headless WebKit does not reproduce real
Safari's on-screen GPU saturation — it held ~60 fps where lane s1's real Safari.app
reads 4–6 fps; trust s1 for absolute severity, this lane for the mechanism + the fix.
(2) This WebKit build crashes the render process under repeated `addStyleTag` mutation
and under the sibling lanes' concurrent DPR2 memory pressure — hence per-condition
fresh browsers and the single-load fixture. (3) `ps` over `com.apple.WebKit.GPU` sums
every lane's WebKit; absolute GPU% is contaminated, the mechanism attribution
(filter:none collapse, WebContent-idle sample, GPU-process locus) is not.
