3 · WHY GATE D IS NOT TRANSPOSED — the refusal is measured, not asserted
--------------------------------------------------------------------------------
The strong preference was to do to GATE D what GATE B does to idle fps: divide by something
the harness measures per host, so a darwin-derived number can gate a runner. GATE B's
denominator is the app-free control's rAF ceiling. It cannot be borrowed here:

  THE FPS CEILING IS A CAP, NOT A THROUGHPUT READING. The runner's control page reports
  p50 16.7, p95 16.7, worst 16.8 ms — three digits of the same number. A clamped quantity
  carries no information about how fast the host computes. Darwin's 132.57 vs the runner's
  60.35 is 130 Hz against 60 Hz; it is a display fact.

It happens to correlate here — 132.57/60.35 = 2.20 against a true boot-work ratio of
(1883/917) = 2.05 measured on total long-task time — and that near-agreement is exactly the
trap. Two refresh rates agreeing to 7% on one host pair is numerology, and its failure mode
is not hypothetical: a CPU-slow 60 Hz host would read a ratio of 1.0 and be handed darwin's
floor, manufacturing a red. Transposition through a capped denominator is refused.

SO THE DENOMINATOR WAS MEASURED INSTEAD. probe.js now runs fixed integer work — 3e7
iterations of `h = Math.imul(h ^ i, 2654435761) >>> 0`, no allocation, no DOM, no engine
builtin, checksum reported so an elided loop cannot pass for a fast host — under whatever
throttle the caller applied, AFTER the boot window has closed (its long tasks start past
WINDOW_MS and are filtered out, so it cannot inflate what it exists to normalise), min of 3.

It is a real throughput instrument, and here is the proof, the same shape as W6's throttle
control (a gates.json copy with cpuThrottleRate 1):

  rate   anchor    boot TBT
  1x      30 ms      17.5 ms
  4x     107 ms     309.5 ms      anchor separation 3.57x — the throttle is applied and
                                  the anchor sees it, unlike the fps ceiling

It is DIAGNOSTIC and gates nothing. ci-subset prints `tbt/anchor` beside the verdict:

  | engine   | throttle | anchor ms | median boot TBT | tbt/anchor |
  | chromium | 4x       | 116       | 256ms           | 2.21       |
  | chromium | 4x       | 109       | 346ms           | 3.17       |
  | webkit   | 1x       | 167       | —               | —          |

Comparable only within one engine at one cpuThrottleRate: TBT subtracts a flat 50 ms per
task, which is not scale-invariant (2.21 at 4x, 0.58 at 1x). Cross-engine is likewise
meaningless — WebKit's JS engine reads 167 ms on the same loop V8 runs in 30.

WHAT WGATE DOES WITH IT: three runner readings decide the question on evidence. If
tbt/anchor holds across host classes, GATE D transposes onto it and the absolute retires. If
it does not, the transposition is refuted BY MEASUREMENT and a runner-derived absolute is
the honest instrument. Either way WGATE reads a number instead of repeating W6's guess.

C.2 · TRANSPOSITION REFUTED, on the record
--------------------------------------------------------------------------------
The hypothesis §3 built the anchor to test was that `tbt/anchor` is portable across host
classes — that the anchor EXPLAINS TBT's variance, so dividing by it would leave a tighter,
travel-safe quantity. The test is one-line falsifiable, and it falsified:

  If the anchor explained TBT's variance, tbt/anchor would be TIGHTER than TBT.
  It is LOOSER — 12.7 % against 5.5 %.

The denominator moved 14.2 % while the numerator sat still at 5.5 %. That is the signature
of a denominator whose variance is INDEPENDENT of the numerator's, and dividing by an
independent noisy quantity strictly adds variance — it cannot subtract any. On this
homogeneous runner class the anchor does not explain TBT, it contributes its own noise, and
a gate is only ever as tight as the noise in the quantity it grades. Transposing would have
bought a floor needing roughly 2.3x the headroom for the same false-red rate, in exchange
for portability to host classes this lane does not run on.

RULED: GATE D STAYS HOST-ABSOLUTE at 1750 for the runner population. The derivation basis in
§4 is UNCHANGED — the worst observed window is still 1368 (post-run medians 1263/1282/1284
all sit below the 1276/1333 the number was cut from), and five medians now corroborate the
band the arithmetic assumed. The anchor column STAYS in the report: it earns its line as the
admissibility instrument in C.3, not as a divisor, and a reader looking at a boot-TBT number
is owed the host's speed beside it.

CORRECTION TO §4, on the record. Step 3 reads "1730.5 -> 1750 ms, rounded DOWN". 1730.5 to
1750 is rounded UP, by 19.5 ms (1.1 %). The number stands and the basis stands; the word was
wrong. Down is the tight direction for a ceiling and C.3 below actually does it.


C.3 · THE CONTROL — GATE D's admissibility ceiling
--------------------------------------------------------------------------------
§8(a) named this the biggest open item: GATE A/B/C refuse a verdict when the app-free
control drops a frame, and GATE D graded straight through. Implemented in ci-subset.mjs as
`ANCHOR_CEILING_MS`, judged BEFORE the threshold, exactly where control-validity is judged
for the frame gates.

  THE CEILING:  max observed runner anchor 177 x 2 = 354  ->  350 ms
                rounded DOWN to grain (down is the tight direction for a ceiling)

  ROUTING:      anchor median > ceiling  ->  instrument failure, exit 3.
                Never a pass, never a breach. GATE D prints INADMISSIBLE with the anchor
                named and issues no verdict at all.

WHY THE HEADROOM IS WIDE — 2x, deliberately:
  - n=3, one runner class, all three quiescent. A ceiling cut close to three samples would
    police ordinary fleet variance, which is the frame control's job and not this one's.
  - The costs are asymmetric. A false refusal costs one retry. A false GRADE costs a red on
    a clean tree — the exact defect the §4 restamp exists to retire.
  - It is meant to catch a DIFFERENT class from the one the samples represent, and a number
    cut to the sample would catch only the sample.

WHAT IT CATCHES, STATED EXACTLY — because the obvious claim is the one that did NOT survive
measurement, and this file does not get to assert the convenient half.

  MEASURED, holds:   the anchor separates THROTTLE RATES (darwin 30 ms at 1x vs 107 ms at
                     4x, 3.57x separation) and HOST CLASSES (darwin 111-120 ms, runner
                     155-177 ms). It is a real throughput instrument.
  MEASURED, fails:   it is NOT a general contention detector. Under 40 synthetic CPU loops
                     this box went to load-average 53.46 against a calm 7.25 and the anchor
                     read 113.5 ms against 116 ms — TBT 281 vs 344 ms. Neither moved.
  MEASURED, partial: during a real mixed-browser contention excursion (the first forced-
                     refusal attempt, sibling waves live) the anchor read 143.5 ms against a
                     calm 116 — up 24 % — while TBT went 344 -> 869 ms, up 153 %. The anchor
                     moves the right way and nowhere near far enough. A 350 ms ceiling would
                     NOT have refused that run.

So `ANCHOR_CEILING_MS` is a HOST-CLASS GUARD — it refuses a host materially slower than the
class 1750 was derived on — and it is NOT the cure for the 3.40x contention exposure §4
banked. That exposure is still open. Saying otherwise would be the proxy-vs-surface mistake
the lessons file names, committed on the instrument built to avoid it.

KNOWN COST, declared. The ceiling converts what would have been an exit 1 into an exit 3 on
any host slower than 350 ms of anchor — so a genuine boot regression on such a host goes
ungraded rather than red. That window is narrow (2x the worst runner reading ever seen) and
it is the same trade control-validity already makes for GATE A/B/C, but it is a trade and it
is written down.

RE-DERIVE AT T8 with more samples, per the floor-timing clause.
