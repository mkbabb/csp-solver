3 · WHY GATE D IS NOT TRANSPOSED — the refusal is measured, not asserted
--------------------------------------------------------------------------------
The strong preference was to do to GATE D what GATE B does to idle fps: divide by something
the harness measures per host, so a darwin-derived number can gate a runner. GATE B's
denominator is the app-free control's rAF ceiling. It cannot be borrowed here:

  THE FPS CEILING IS A CAP, NOT A THROUGHPUT READING. The runner's control page reports
  p50 16.7, p95 16.7, worst 16.8 ms — three digits of the same number. A clamped quantity
  carries no information about how fast the host computes. Darwin's 132.57 vs the runner's
  60.35 is 130 Hz against 60 Hz; it is a display fact.

It happens to correlate here — 132.57/60.35 = 2.20 against a true boot-work ratio of
(1883/917) = 2.05 measured on total long-task time — and that near-agreement is exactly the
trap. Two refresh rates agreeing to 7% on one host pair is numerology, and its failure mode
is not hypothetical: a CPU-slow 60 Hz host would read a ratio of 1.0 and be handed darwin's
floor, manufacturing a red. Transposition through a capped denominator is refused.

SO THE DENOMINATOR WAS MEASURED INSTEAD. probe.js now runs fixed integer work — 3e7
iterations of `h = Math.imul(h ^ i, 2654435761) >>> 0`, no allocation, no DOM, no engine
builtin, checksum reported so an elided loop cannot pass for a fast host — under whatever
throttle the caller applied, AFTER the boot window has closed (its long tasks start past
WINDOW_MS and are filtered out, so it cannot inflate what it exists to normalise), min of 3.

It is a real throughput instrument, and here is the proof, the same shape as W6's throttle
control (a gates.json copy with cpuThrottleRate 1):

  rate   anchor    boot TBT
  1x      30 ms      17.5 ms
  4x     107 ms     309.5 ms      anchor separation 3.57x — the throttle is applied and
                                  the anchor sees it, unlike the fps ceiling

It is DIAGNOSTIC and gates nothing. ci-subset prints `tbt/anchor` beside the verdict:

  | engine   | throttle | anchor ms | median boot TBT | tbt/anchor |
  | chromium | 4x       | 116       | 256ms           | 2.21       |
  | chromium | 4x       | 109       | 346ms           | 3.17       |
  | webkit   | 1x       | 167       | —               | —          |

Comparable only within one engine at one cpuThrottleRate: TBT subtracts a flat 50 ms per
task, which is not scale-invariant (2.21 at 4x, 0.58 at 1x). Cross-engine is likewise
meaningless — WebKit's JS engine reads 167 ms on the same loop V8 runs in 30.

WHAT WGATE DOES WITH IT: three runner readings decide the question on evidence. If
tbt/anchor holds across host classes, GATE D transposes onto it and the absolute retires. If
it does not, the transposition is refuted BY MEASUREMENT and a runner-derived absolute is
the honest instrument. Either way WGATE reads a number instead of repeating W6's guess.


4 · THE RESTAMP — arithmetic
--------------------------------------------------------------------------------
BASIS. Runner, head 6d612ec5, quiescent (4 cpus, load 0.92 -> 1.96, chromium control fps
60.35 with long33 0). Two VMs, six windows:

  job A (original)   median 1276 ms
  job B (rerun, 91643242319, artifact perf-subset-report.txt)
                     1368 / 1256 / 1333 -> median 1333 ms

  worst window          1368 ms
  worst median          1333 ms
  within-run spread     1368/1256 = 1.089
  cross-VM spread       1333/1276 = 1.045

STEP 1 — spread.        1368 x 1.10 = 1504.8      (covers the larger observed spread, n=2 VMs)

STEP 2 — no control.    1504.8 x 1.15 = 1730.5

  GATE D is the one gate in this lane with no app-free denominator. The control-validity
  law refuses a verdict when the control page drops a frame — that protects A, B and C. A
  contended boot TBT is graded straight through as a fact about the bundle, and ci.yml
  never retries an exit 1. THE EXPOSURE IS MEASURED, in §2's table: same dist, same 4x rate,
  frame control clean and EXIT=0 in every one of those runs, and the median still moved
  256 -> 871 ms (3.40x) as the 1-minute load went 10 -> 41.

  1.15 buys the first slice of a 3.40x exposure. It is not a cover for it. The cure is a
  control, not a bigger number, and the instrument for one is now in the harness.

STEP 3 — grain.         1730.5 -> 1750 ms, rounded DOWN (the conservative direction for a
                        ceiling; the file's siblings are round: 1200, 52, 0.90).

TRIPWIRE RETAINED. 1750 - 1333 = 417 ms of headroom over the worst quiescent runner median.
One new synchronous boot task of X ms unthrottled contributes ~(4X - 50) ms, so the gate
trips at X >= 117 ms — against an app whose own largest boot task is ~149 ms unthrottled
(595 ms at 4x on the runner). W6's declared class is caught by a comfortable margin.

WHAT THE INCUMBENT ACTUALLY WAS. 1200 sat BELOW the clean-tree reading on the only host that
runs this lane. It was never a floor; it was a false-red machine, and its first field
contact is what proved it. This is the lessons-file's proxy-vs-surface rule read from the
config end: a threshold derived on a host it will never grade is a guess wearing a number's
clothes. 1750 is derived where it is graded.

DARWIN ASYMMETRY, DECLARED. 1750 is 6.8x darwin's calm median — on darwin this gate is
loose. That is by construction: the ubuntu runner is the population GATE D grades, the
darwin perf-rig is a separate manual lane, and the asymmetry is the exact thing the
transposition in §3 would remove once it has evidence. Flagged for WGATE.
