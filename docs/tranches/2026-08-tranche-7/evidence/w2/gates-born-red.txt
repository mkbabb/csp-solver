  · ".icon-sublabel and .ctrl-btn clear 4.5:1 (light)"   PASSED  chromium + webkit
  · ".icon-sublabel and .ctrl-btn clear 4.5:1 (dark)"    PASSED  chromium + webkit

  THIS ARM IS GREEN TODAY AND SAYS SO. It is a FLOOR ROW, not a defect row: it exists so a
  future token nudge cannot cross 4.5 in silence. 0.16 of headroom is the whole margin.

    light   worst 4.66:1 — "Deal" .icon-sublabel   rgb(115,115,115) on rgb(253,253,252)
    dark    worst 7.68:1 — "Deal" .icon-sublabel   rgb(168,166,159) on rgb(19,18,17)
    n = 20 painted samples per theme; both engines report the same numbers to the hundredth.

  4.66:1 light reproduces the audit's figure exactly.

  Both families are NORMAL text at every width they paint (sublabels 14.4–16.4px regular,
  chips 20px regular — under 18.66px bold / 24px regular), so one 4.5 floor covers them.

  THE RESOLVER is the only thing this row needed building: `color-mix(…, transparent)`
  computes to `color(srgb r g b / a)`, and a naive `rgb()`-only parser reads that as black
  and reports a fictional ratio. The parser takes `rgb()` / `rgba()` / `color(srgb …)` /
  `#hex` / `transparent`, composites the backdrop bottom-up through every ancestor layer to
  the first opaque one, then composites the text colour over it. At THIS tree both targets
  happen to resolve to plain `rgb()` in both engines — the resolver is there for the tokens'
  next move, which is what a floor row is for.

  The theme is ASSERTED, not assumed: each row polls `html.dark` to the expected value
  before measuring, because `useDark` reads `prefers-color-scheme` only while its storage
  key is unset and a row that measured the wrong theme would be reporting the other row's
  numbers.
