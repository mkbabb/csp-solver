--------------------------------------------------------------------------------
2 · THE FIX
--------------------------------------------------------------------------------
web/frontend/perf-rig/ci-subset.mjs:

  · per-engine outcomes ACCUMULATE — `results` / `instrumentFails` / `setupErrors`.
    Nothing in the engine loop returns; every failure path pushes and `continue`s.
  · the verdict block is unconditional. Every measured result is graded before any
    exit is chosen.
  · the exit code is the WORST FACT in the run, in this order:
        1 (a breach, anywhere) > 2 (setup) > 3 (instrument) > 0
    A breach outranks an instrument failure because a breach is a fact about the
    BUNDLE and an instrument failure is a fact about the HOST. A bad host cannot
    un-measure a bad bundle.
  · engine NAMES are validated before the loop opens, so a typo can no longer be the
    early return that eats a verdict either.
  · the report names what did not measure — `NOT MEASURED [engine] — why` — so a RED
    with one engine missing cannot be misread as a full-matrix red.

5 · THE WEBKIT LONGTASK ARM — exit 2, never a vacuous pass
--------------------------------------------------------------------------------
W6 §vacuous gates: "WebKit lacks `longtask` — any long-task assertion on the webkit
lane is vacuous. Assert support first and exit setup-error otherwise, matching
ci-subset.mjs's exit-2 discipline."

Support is asserted IN THE PAGE (`PerformanceObserver.supportedEntryTypes`) and the
bit travels with the reading, because an engine that reports no long tasks because it
cannot see them is indistinguishable from a clean boot unless it says so. Measured:

    chromium   longtask yes   tbt 218-357ms over the 3000ms boot window at 4x CPU
    webkit     longtask NO    tbt —   -> row prints NOT MEASURED, never PASS

A run where NO engine could measure it refuses to issue a verdict at all:

Note what the same run does NOT do: webkit's own GATE A/B/C rows are graded and pass,
and they still stand — the setup error is scoped to the row that could not be measured.
That is the same discipline as §2: every measured thing is graded, and the exit code is
the worst fact, not the first one.

The third mouth of the same rule — throttling. GATE D's floor is derived at
boot.tbt.cpuThrottleRate (4x). If CDP throttling is requested and cannot be applied,
the run exits 2 rather than measuring at 1x: an unthrottled number read against a
throttled floor is a different measurement, not a lenient one. The throttle's own
control, same box, same script, gates.json copy with cpuThrottleRate:1 —

    1x   bootTbt tbt 5ms / 4ms   (1 task, longest 55ms)
    4x   bootTbt tbt 287/357/316ms   (10-11 tasks, longest 248-274ms)

— a 60-70x separation, so the rate is demonstrably applied and not silently dropped.

--------------------------------------------------------------------------------
6 · WHAT THIS DOES NOT CLOSE
--------------------------------------------------------------------------------
ci.yml's own prose still claims "chromium's verdict (computed before webkit) gates via
exit 1 whenever it breaches" (ci.yml:1244-1245). That sentence was FALSE at HEAD —
§1 is its disproof — and it is still the wrong reason now: what makes a chromium breach
gate is that every measured result is graded, not that chromium runs first. `--engines`
order is a caller's argument, not a law. The strike + replacement is filed as a W6
wiring request; W6's executors do not edit ci.yml.
